學習目標

這一節考的是「提出合適的方案」

考綱要求你依情境推薦 project implementation，範圍包含 company-managed、team-managed、project templates 與 shared configuration。你需要能說明為什麼這個方案符合需求，以及它會帶來什麼影響。

讀完後，你應該能回答：
誰負責設定？是否要跨 project 共用？團隊用固定週期還是持續處理工作？修改共用設定會影響誰？
先對齊版本與名詞
官方考綱 PDF 內文版本是 V2｜March 2023，檔名的 2026 不代表內容改版。本課沿用考綱的 project、issue、issue type；2026-09-07 讀取的官方頁面已大量使用 space、work item、work type。以下是這組教材中的新舊名稱對照，不能推定實際考題已全部改名。
考綱常用名稱目前說明頁常見名稱閱讀時怎麼理解
projectspace本課指 Jira 中管理工作的容器；不要與 Atlassian Home 的 project 混為一談。
issuework item一筆要追蹤的工作。
issue typework type工作的分類，例如 Bug、Task。
先備知識

用一個訂餐網站，認識 Jira 的基本結構

假設團隊要做一個訂餐網站。「讓使用者付款」是一筆工作，「修正付款失敗」也是一筆工作。Jira 幫你記錄由誰負責、做到哪裡，以及接下來要做什麼。

Project：放工作的地方

例如 訂餐網站 project，裡面有 ORDER-1、ORDER-2 等 issues。它還有控制這些工作如何運作的設定。

Workflow：工作經過哪些狀態

例如 To Do → In Progress → Done。status 是當下的位置；transition 是從一個狀態走到另一個狀態的動作。

Board：把工作攤開來看

像把工作卡片放在不同欄位。board 是呈現與管理工作的視圖，不能直接把「選哪種 board」當成「由誰管理設定」。

Scheme：可重複使用的設定規則

例如 permission scheme 定義誰能執行哪些動作。先把 scheme 想成「設定的對應規則」，稍後再看多個 project 如何共用。

以上是原創入門例子；scheme 與角色的關係參考 來源 5。

核心觀念

差別在設定的管理方式，不能只看人數

TEAM-MANAGED

團隊自己調整工作方式

適合想快速開始、獨立試驗流程的團隊。project admin 可以自行管理該 project 的許多設定，不必每次都找 Jira admin。

情境：訂餐網站的實驗小組想先試一週「待驗證」流程，再決定是否保留。

COMPANY-MANAGED

集中管理，讓不同團隊遵循共同規則

適合需要跨 project 標準化，或較複雜的 permissions、workflows 設定。schemes 與 screens 由 Jira admin 管理。

情境：付款、物流、會員三個團隊都必須採用同一套審核流程。

核心選型依據：來源 1；例子為教學設計。

比較項目Team-managedCompany-managed
管理重心project 內的自主設定由 Jira admin 管理可共用的設定
設定的影響範圍本地設定以該 project 為範圍修改共用設定，影響所有引用它的 projects
Permissions以該 project 的 roles 管理；設定各自獨立permission scheme 可對應 users、groups、project roles
建立權限一般使用者預設可建立，但 Jira admin 可透過 global permissions 限制由 Jira admin 建立
功能配置可在使用過程中開關 backlog 等功能功能組合與建立時使用的 template 有關
適合的需求自主調整、獨立設定、快速開始標準化、共用設定、集中控管

比較依據：建立權限、功能差異、設定與 permissions。

不要把管理權限讀成「所有人都能亂改」。
team-managed 仍有 roles 與 permissions。company-managed 也有 project admin；「schemes 與 screens 要找 Jira admin」不等於「project admin 什麼都不能做」。本課先辨認責任範圍，詳細權限留到 620.3。

要在目前介面確認類型，可以找 project／space 名稱旁的 More actions（⋯），查看選單底部的 Team-managed 或 Company-managed 標示。舊介面的位置可能不同。[1]

第二個判斷維度

Template 決定起步方式

Template 提供預先配置的 issue types、workflows 與相關功能。它能省去從零設定的時間；選型時仍要另外確認管理方式與共用需求。[3]

Template白話理解原創情境
Scrum將工作放入固定長度的 sprint，先規劃、再執行與檢視。每兩週挑一批訂餐功能，完成後檢查交付成果。
Kanban工作持續流入，依容量拉進來處理；注意 WIP。網站維運問題陸續進來，團隊持續處理。
Bug tracking集中記錄、排序、指派及解決 bugs。先建立產品缺陷追蹤清單，安排修復優先順序。

Backlog 是尚待安排的工作清單；sprint 是固定長度的工作週期；WIP（work in progress） 是已開始、尚未完成的工作量。這些名詞描述的是工作節奏，不是管理權限。

同樣 Scrum，也可能選不同類型

甲團隊每兩週交付，想自己改流程 → 可考慮 team-managed ＋ Scrum。

乙團隊每兩週交付，必須沿用公司的共用流程 → 可考慮 company-managed ＋ Scrum ＋ shared configuration。

看到這些字，先想到工作節奏

fixed-length iterations、regular cadence → 想想 Scrum。

continuous flow、limit work in progress → 想想 Kanban。

再回頭找誰管理、是否共用等線索。

Template 用途參考 來源 3。上面的組合是依需求推導的教學建議，不代表每個站台都提供完全相同的 template 清單。

官方功能差異頁指出 company-managed 的功能組合與 template 綁定；這不等於所有設定都不能調整。閱讀時要區分「template 的預設功能」與「後續可配置的 workflow、screen 或 board」。[4]
最值得動手理解的地方

Shared configuration：一起用同一套規則

建立 company-managed project 時，Jira admin 可以選擇共用現有 project 的設定。官方列出的共用範圍包含 issue types、workflows、screens、fields、permissions、notifications；此建立選項不提供給 Free plan。[2]

把它想成「大家引用同一份規則」。例如 A、B 共用 workflow，修改被共用的 workflow 時，兩邊都受到影響；不能把它當成替 B 複製一份之後就各自獨立。

原創示意：共用設定不等於共用 issues。A、B 仍然各有自己的工作資料。

試試看：加入 Review 會改到誰？

簡化的教學模擬，不會連線或修改 Jira。
Project A
To Do → In Progress → Done
Project B
To Do → In Progress → Done
A、B 引用同一個 workflow。按一下「加入 Review」觀察兩邊。

三件容易混淆的事

情況能否直接推定會一起變？
兩個 project 都選 Scrum不能。光知道同樣 template，還不足以判斷是否引用同一個設定。
兩個 project 明確共用同一個 workflow會。修改被共用的 workflow，兩邊都受影響。
兩個獨立設定剛好同名不能。同名不等於同一個設定物件。
推理練習：如果只有 B 想改流程，先請 Jira admin 確認共用關係，評估替 B 配置獨立設定。不要直接修改大家共用的設定，卻期待只有 B 改變。
解題方法

把題目拆成三個問題

  1. 誰要控制規則？需要集中管理、複雜 permissions 或 workflow 嗎？先考慮 company-managed。需要團隊獨立調整嗎？考慮 team-managed。
  2. 是否必須共用既有設定？若明確要求多個 projects 沿用同一套設定，考慮 company-managed ＋ shared configuration，並確認 Jira admin 與方案限制。
  3. 團隊怎麼交付工作？固定週期看 Scrum；持續流入看 Kanban；主要是缺陷追蹤看 Bug tracking。再檢查是否符合題目所有限制。

教學判斷樹，不是 Jira 的實際建立畫面。如果兩種需求同時出現，優先處理「必須」符合的約束，別只抓一個關鍵字。

「先隨便選，以後直接切換」不是好答案。
官方指出不能把 team-managed 直接原地轉成 company-managed；需要建立目的 project、搬移工作並處理設定。搬移還可能失去估算與報表歷史，因此應在選型時評估。這是補充觀念，不是本課的搬移操作練習。[6]
實際操作觀察

花 10 分鐘，把名詞對上畫面

使用練習站台即可。這一輪重點是辨認選項；不需要為了完成教材在公司正式環境建立 project。

  1. 進入建立頁面目前官方指引是側邊導覽 Spaces → Create space；若你的站台仍叫 Projects，尋找對應的 Create project。[2]
  2. 比較 Scrum 與 Kanban template閱讀預覽，指出哪個以固定 sprint 為重心。把自己的需求寫成一句話，再選擇適合的 template。
  3. 找出管理方式選項辨認 Company-managed 與 Team-managed。若缺少建立權限，記錄觀察結果，不必為練習調整正式站台權限。
  4. 觀察共用設定選項具備 Jira admin 權限且使用支援方案時，選 Company-managed，找 Share settings with an existing space（舊稱 project），觀察可選的來源。完成觀察後可以直接取消。
  5. 說出方案與理由例如：「我們每兩週交付，且三個團隊必須共用規則，所以選 company-managed、Scrum，並由 Jira admin 配置 shared configuration。」
目前頁面的 Rovo，需要一起背嗎？

補充閱讀的 Create a new space 已包含用 Rovo 產生 space 的流程、credits 與使用量管理；設定差異頁也提到 Rovo 導覽設定。本課已讀過這些段落，但這份考綱的 620.1.1 沒有明列 Rovo，因此不把它列為本課必記內容。這不代表能保證實際考試永遠不涉及新功能。

用 Demo site 跟做

用兩個 projects，證明 shared configuration 的影響

實作前請準備 Jira／site admin 與一般測試帳號。本節可進一步實作；確認 demo site 的方案支援 shared configuration，再建立隔離的練習設定。

  1. 先建立 Company-managed A例如 ACP620 Shared A。檢查它使用哪些 schemes；如果 demo site 有其他展示用 projects，不要直接修改它們正在用的 workflow。
  2. 建立 Company-managed B選 Share settings with an existing project／space，指定 A。建立後核對 A、B 的 workflow／scheme 名稱或識別資訊，確認真的共用。
  3. 各建立一筆 TaskA、B 都放一筆簡單工作。先觀察兩邊都有相同 workflow，但 issue keys 與內容不同。
  4. 修改隔離的共用 workflow加入 Review status 與適當 transitions，依編輯器要求儲存／發布。再回 A、B 檢查兩者 issue workflow 都反映變更。Board 是否出現對應欄位仍需檢查 column mapping，不能只看 board 就判定 workflow 沒改成功。
  5. 記錄三個答案共用的是什麼？哪兩個 projects 受影響？工作資料是否被合併？正確觀察是：共用設定變更、兩邊受影響、issues 仍分開。
把「本地獨立設定」當成對照組：另外的 team-managed project 不會因這個共用 workflow 的修改而同步變更。之後在 620.1.2 練習它的本地設定。
理解檢查

先選答案，再打開解析

以下是原創練習，不是官方題庫或實際考題。每題選一個最合適的答案。

1．一個實驗小組每週改流程，希望由自己維護，沒有跨 project 共用需求。最適合哪個管理方式？
  1. Team-managed
  2. Company-managed ＋ shared configuration
  3. 只要選 Scrum 就能滿足管理需求
查看答案與各選項解析

A。自主調整是主要需求。B 增加了題目沒有要求的共用關係；C 只回答工作節奏，沒有回答設定由誰管理。

2．六個產品 project 必須使用同一套 workflow，將來調整時也要一致。該推薦什麼？
  1. 六個 team-managed，將 workflow 命名成相同名稱
  2. Company-managed，使用 shared configuration
  3. 六個 project 選相同 template 就足夠
查看答案與各選項解析

B。題目要求持續共用設定。A 的同名設定不會因此成為同一份；C 的 template 名稱本身不能證明共用關係。

3．A、B 共用一個 workflow。Jira admin 在這個共用 workflow 加入 Review，誰會受影響？
  1. 只有 A
  2. A 與 B
  3. Jira 裡的所有 projects
查看答案與各選項解析

B。影響引用該 workflow 的 projects。A 忽略共用關係；C 把影響範圍擴大到未引用的 projects。

4．團隊持續接收工作，希望限制同時進行的數量。單就工作節奏，哪個 template 最合適？
  1. Scrum
  2. Kanban
  3. Company-managed
查看答案與各選項解析

B。持續流動與 WIP 是線索。A 更偏固定週期規劃；C 是管理方式，不是本題在問的 template。

5．使用 Free plan 的一般 project admin，要建立與別的 project 共用設定的新 project。哪個說法正確？
  1. 只要能管理 project 就能建立 shared configuration
  2. 改用 team-managed 即可共用 schemes
  3. 此功能需要 Jira admin，且該建立選項不適用 Free plan
查看答案與各選項解析

C。權限與方案都要符合。A 混淆 project admin 與 Jira admin；B 不符合共用設定的建立方式。[2]

6．只有三個人的團隊，卻必須沿用其他部門的共用設定。每兩週交付。哪個方案更合適？
  1. 人少，所以一定要 team-managed
  2. Company-managed ＋ Scrum，並確認 shared configuration
  3. Kanban，因為所有小團隊都適用
查看答案與各選項解析

B。共用設定是管理方式的約束；兩週交付提供 Scrum 的線索。A、C 都把人數誤當成決定條件。
