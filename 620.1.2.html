從第一張工作卡片，到正確的存取權限

本節要學會建立與設定 team-managed project、解釋 access 與 permissions，以及加入使用者。貫穿案例是 訂餐網站 Demo：開發者要編輯工作，顧問只參與討論，負責人管理設定。

完成標準：你能建立一筆工作並移動狀態；能說出 Open／Limited／Private 的差別；能用一般測試帳號證明角色設定真的符合預期。

1．先建立一個可放心練習的 project

  1. 準備環境與名稱使用 demo site。練習名稱建議「ACP620 Team Lab」，key 建議 TMLAB；若已被使用，另選唯一名稱與 key。project 是容器，key 是工作識別碼的前綴，例如 TMLAB-1。
  2. 找到建立入口Spaces／Projects → Create space／Create project。一般使用者預設可建立 team-managed，但 Jira admin 可透過 Create team-managed spaces（舊稱 projects）global permission 限制。Admin 可建立，不代表其他人也可建立。
  3. 選 template 與管理方式先選 Kanban，並確認 Team-managed。官方不同導引的選項順序不一致；重點是最後確認這兩項。Kanban 便於第一次直接觀察卡片，稍後再試 sprints。
  4. 輸入名稱，完成建立依畫面按 Next 或 Create；若出現 repository／Confluence 連結選項，初次練習可略過。建立後由名稱旁 ⋯ 確認 Team-managed。
  5. 記住兩個入口Board 是處理工作的地方；Project settings／Space settings 是設定規則的地方。Details 管基本資料，Access 管人與角色。
Project 名稱並非對 Jira admin 隱藏。即使 Private，名稱也不要當成存放機密資訊的欄位。Free plan 不能編輯本課後面所需的 permissions／roles；即使你有 admin 權限，也不能繞過方案限制。

2．建立第一筆 issue，理解 board 與 status

建立「完成訂餐首頁」這筆 Task。Summary 寫工作要做什麼；Description 放驗收條件，例如「能看到餐點名稱、售價與加入購物車按鈕」。Assignee 是負責人，Reporter 是回報者，兩者不必相同。

In Progress
TMLAB-2
設計餐點列表Task · 正在處理

確認測試資料Task · 已完成

原創概念圖，非 Jira 截圖；卡片位置表示工作進度。

  1. 在 Board 新增未啟用 Sprints 時，點欄位底部 Create work item／Create issue，填 Summary，確認 Task，按 Create。也能使用全域 Create。
  2. 移動工作把卡片由 To Do 拖到 In Progress，再移到 Done。這是在改 status，不是在改 issue type。按 Command（Mac）／Ctrl（Windows）可多選卡片。
  3. 啟用 Sprints 後比較啟用後先到 Backlog 建立 issue，加入 sprint，再開始 sprint。若 sprint 還沒開始，board 可能沒有卡片；官方入門頁也指出此時不能直接在 board 建立工作。
概念意思例子
Status一筆工作的具體狀態Developing、In review
Status category將 status 歸納到三大類To do、In progress、Done
ColumnBoard 上呈現工作的欄位初始配置常與 status 一對一；進階可配置多個 statuses
初始 team-managed board 的最左欄對應 To do，最右欄對應 Done，中間對應 In progress。不要把欄位文字「改名 Done」當成完整驗證；請檢查工作實際 status 與 status category。

3．把 board 調整成團隊的流程

操作怎麼做操作後觀察
新增欄位最右欄旁 Create column，新增 Review入門的一對一設定會一起產生同名 status。
改名／排序點欄名改名；拖曳欄位標題排序欄位順序表達流程順序，檢查最右側完成欄。
刪除欄位欄位 ⋯ → Delete若有 issues，要指定移到哪個 column／status；Backlog 中相關 issues 也會受影響。
刪除 Done 欄同上，但先理解完成狀態映射Board 仍需要 Done；接收工作的欄位會承接 Done 的含義。初次練習建議保留原 Done 欄。
限制進行中工作量Kanban 欄位 ⋯ → Set column limit用來提醒 WIP 過多；不要把視覺限制推定成禁止建立工作的權限。
篩選與分組Filter（Shift + F）、搜尋、Assignee filter、Group by只是在調整視圖；看不到卡片時先清除篩選。
卡片封面卡片 ⋯ → Select cover；View settings → Card cover可選顏色或圖片；只影響辨識方式，不是權限或進度。

清空 Done 欄，不等於刪除 issue

Kanban 模式下，移到 Done 滿 14 天的工作會自動從 board 清除。project admin／Jira admin 也可在 Done 欄 ⋯ → Clear Done work items。啟用 Sprints 時不能使用這個手動清除動作；完成 sprint 時，最右側完成欄的工作會從 board 清除，不會回到 backlog。

清除後可用 See all Done work items 或搜尋找回；parent 清除時，subtasks 也會一起從 board 清除，即使 subtask 狀態尚未完成。因此「消失」要先判斷是視圖清除、篩選、sprint 還沒開始，還是真的被刪除。

Team-managed 設定的範圍

本地 issue types、workflows、fields 屬於這個 project。建立的 fields 可供該 project 不同 issue types 使用，也可用於站台搜尋或 dashboard gadgets；能搜尋到，不代表變成跨 project 共用 field。project admin 可在本地管理 fields；目前官方也說 Jira admin 可在 Jira admin settings 集中管理它們。

Backlog、Sprints、Estimation、Releases and versions 等功能可依需要開關。官方管理入口頁另外連到 notifications、Bitbucket、Marketplace apps、workflow rules、work type restrictions 與 work item limits；這些是延伸設定入口，不要因為在目錄出現就把它們當成建立 project 的必做步驟。

4．權限先分三層，才不會一直猜

官方 permissions 頁以 access level 與 role 為兩個主要設定。實際排查還要先看使用者是否加入站台、是否具備功能要求的 app access。這些不是同一回事。

層次它回答什麼例子
Site／app access是否能進入站台、使用所需 Jira 功能？找到人並加入 project，不一定就授予完整 app access。
Access level對站台上其他已登入的人，預設給什麼？Open 預設 Member；Limited 預設 Viewer。
Roles特定人或群組額外取得哪些權限？某位顧問是 Viewer；開發群組是 Member。
Access level未個別加入的一般站台使用者適合的教學情境
Open預設 Member；可查看、建立、編輯工作接受公司內部廣泛共同參與。
Limited預設 Viewer；可查看、留言，不能建立或編輯 issues讓其他團隊知道進度，只有核心團隊執行工作。
Private不因 access level 自動取得一般成員角色；只開放加入的人及 Jira admins 等適用存取僅讓指定團隊參與。
Open 不是公開到全網。team-managed 不支援 anonymous access。Private 也不是阻止 Jira admin：具備 Administer Jira global permission 的人仍可存取設定。一般使用者能做什麼，請用非 admin 帳號驗證。

5．Role 是一組權限，而且是「加上去」

預設三種角色是 Administrator、Member、Viewer。Viewer 名字看起來像「只能讀」，但官方權限表還授予留言、附加檔案、編輯或刪除自己的留言／附件等能力；不能只看角色名稱猜權限。

關鍵公式：access level 給的角色 ＋ 個人角色 ＋ 群組角色。
在 Open project 把小明指定成 Viewer，不能拿掉他因 Open 得到的 Member 權限。若要讓一般人只看、核心成員可編輯，可改 Limited，再明確加入核心成員為 Member。這是依官方加總規則推導的配置。

常見錯誤配置

Open ＋ 指定小明 Viewer

你期待：只能看。
實際：仍繼承 Member 的編輯能力。

符合需求的配置

Limited ＋ 開發群組 Member

一般站台使用者：Viewer。
開發群組：額外取得 Member。

  1. 開啟 AccessProject／Space settings → Access。先確認目前的 access level；要調整時找 Change project／space access，選好後按 Change。
  2. 加入已在站台的人Access → Add people，輸入姓名、group 或 email，選角色，按 Add。也可從 Share 調整 access 與角色。找不到人時，先由 Jira admin 邀請其加入站台，不要反覆改角色碰運氣。
  3. 調整角色Access 表格的 Role 下拉選單可勾選角色；一個人或群組可有多個角色。某些角色能力需要 Jira app access，請由負責使用者管理的 admin 檢查。
  4. 建立自訂角色Manage roles → Create role，填名稱與描述，勾選需要的 permissions，再 Create。可先 Duplicate 現有角色作為起點。
  5. 修改與刪除角色自訂角色可調整並 Update，修改對該角色所有人都生效。預設 Administrator／Member／Viewer 不能編輯或刪除，但可複製。刪除自訂角色也可能影響 notifications 與 work item restrictions，且不等於把該角色的人移出 project。
  6. 移除使用者Access 表格找到人 → Remove。還要檢查 Open／Limited 預設存取、群組角色；移除 project 成員也不等於移除站台帳號。
互動實驗 · 一般使用者

換個 Access level，看看角色怎麼加總

模型假設：已具備所需 Jira app access、不是 admin、沒有其他群組或個別 issue restrictions。這是教學模擬，不會修改 demo site。

Open → Member＋直接 Viewer→取得 Member 能力
查看與留言可以
建立與編輯 issue可以
管理 project 設定不可以

指定 Viewer 不會抵銷 Open 預設給的 Member 權限。

試做：先改 Limited，再勾選群組 Member。觀察較低的直接角色為什麼不能限制較高的群組權限。

6．完整預設權限表：按動作查，不用一次硬背

被加入 project 的使用者會先取得 Browse project、View project 與 View issues 的基本存取。以下將指定官方權限表完整整理，沿用考綱的 issue／project 用字；✓ 為預設授予，— 為該角色未授予。這不是有效權限的否決表：其他角色仍可能授權。官方表的一列寫作 Edit their own worklog work items，下方說明使用 work log entries；本表以該動作說明統一用語。

三種動作群組可幫助理解：Collaborate on issues 是留言、附件等協作；Work on project issues 是建立、指派、編輯、轉換、連結、工時等日常工作；Manage project issues 包含較強的管理動作。仍以逐項勾選與官方表為準，不能推定一個群組名稱就包含所有相關能力。

兩個進階但實用的判斷

能被指派：team-managed 沒有照搬 company-managed 的 Assignable user 設定。官方說角色只要被授予 Work on project issues 集合中的任一權限，該角色的人就能成為 assignee。

複合條件：Move issue 需要來源搬移權限，也需要目的地建立權限；有 Edit issue 不代表能改 Reporter 或 Due date。遇到錯誤時，把「那個具體動作」拆出來檢查。

7．Demo site 驗證：不要用 admin 假裝一般人

準備一個一般測試帳號、你的 admin 帳號，以及剛建立的 TMLAB。請使用已授權的測試身分；以下是教材步驟，沒有替你新增人員或發送邀請。

實驗設定與測試動作預期結果
A：Open 疊加TMLAB 改 Open；把一般測試帳號明確設 Viewer；登入測試帳號試建立 issue仍可能建立與編輯，因為繼承 Member。
B：Limited改 Limited；讓測試帳號只保有 Viewer，檢查群組沒有額外角色可以查看與留言，不能建立 issue。
C：核心成員在 Limited 明確加測試帳號為 Member可以建立、編輯；因額外角色取得能力。
D：Private改 Private；移除該測試帳號的直接角色及授權群組關係一般測試帳號無法在搜尋／目錄看到 project；不要用 Jira admin 判斷。
E：View 與 Delete重新加 Viewer；上傳測試附件並留言可操作自己的附件／留言，不應能刪除別人的留言。
F：自訂角色Private 中建立只授予所需權限的自訂角色，加入測試人逐項測試；不要同時保留 Member，否則較大權限掩蓋自訂角色限制。
如果結果不同，依序查：是否用對帳號 → global admin 身分 → access level → 直接角色 → 群組角色 → app access → 方案 → 個別 issue restrictions。不要為了通過測試直接把所有 permissions 全打勾。

8．情境題與解析

1．Open project 指定小明為 Viewer，為什麼仍可編輯？

  1. Viewer 本身可以編輯所有 issues
  2. Open 給了 Member，角色是加總
  3. Jira 壞了
查看答案與解析

B。Viewer 沒有 Edit any issue，但 Open 的 Member 有。先檢查繼承來源，不要把加總誤解成覆寫。

2．移除 Access 表中的某人，就保證無法查看嗎？

  1. 是
  2. 否，可能仍有 access level 或群組授權
查看答案與解析

B。移除直接角色只處理一個來源，還要檢查 Open／Limited 與群組。

3．Viewer 預設可以做什麼？

  1. 只看，不能留言
  2. 留言、附加檔案、編輯自己的留言
  3. 刪除所有人的留言
查看答案與解析

B。官方逐項表比簡短角色描述更精確。A 太窄，C 需要較高權限。

4．Member 想把工作搬到另一個 project，只有來源的 Move permission 夠嗎？

  1. 夠
  2. 還需要目的 project 的 Create permission
查看答案與解析

B。搬移要同時檢查兩邊。

5．Board 空白，但 Backlog 有工作，剛啟用 Sprints。先查什麼？

  1. 是否有開始 sprint
  2. 先刪 project 重建
查看答案與解析

A。這是視圖與 sprint 的關係，不代表資料遺失。

6．刪除自訂角色會自動刪掉使用者帳號嗎？

  1. 會
  2. 不會
查看答案與解析

B。角色、project 成員、站台帳號是不同層次；角色刪除還可能影響 notifications 與 restrictions。
