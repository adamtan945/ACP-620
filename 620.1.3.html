本課沿用考綱的 project／issue／issue type；目前官方介面常稱 space／work item／work type。操作入口可能因導覽更新不同，請依功能名稱對照。練習使用隔離的 demo site；權限與方案限制分開檢查。

這節要解決：一件大事，該怎麼拆成可追蹤的工作？

考綱要你依 business requirements，推薦 company-managed project 的 issue type configuration，理解 Epic、base／standard 與 sub-task 的特性。先學怎麼分類，再理解管理員怎麼讓這些類型可用。

完成標準：你能替一個需求畫出 Epic → standard issue → subtask；能判斷何時該用獨立 Task；能說明「子工作全做完，父工作才能完成」需要另外配置 workflow condition。

1．Issue type 是工作種類，不是工作狀態

同一張工作卡片可以同時有「種類」與「進度」。例如「付款按鈕失效」是 Bug，目前 In Progress。修完後它還是 Bug，只是 status 變成 Done。

你要表達的事情應該用什麼例子
這是缺陷還是一般工作？Issue typeBug／Task／Story
目前做到哪裡？StatusTo Do／In Progress／Done
這是誰的大工作的一部分？Parent／child relationshipStory 隸屬 Epic；Subtask 隸屬 Task
先做哪件事？Priority 或工作排序High priority；在 backlog 中往前排

使用不同 issue types 的目的，是讓搜尋、排序、進度追蹤與分析有共同語意。不要把所有工作都叫 Task，卻期待之後能自動分辨 defects 與新功能；也不要為每個客戶建立一種 issue type，讓種類失去穩定意義。

2．先熟悉預設三層階層

原創範例：Epic 是較大的交付成果；Story、Bug、Task 都在同一個 standard 層級。Subtask 才是其下一層。

層級功能用訂餐網站理解
Epic較大的工作或 initiative，聚合多筆 standard issues完成線上訂餐體驗
Base／standard日常討論、執行與估算的工作；常見 Story、Task、Bug用信用卡付款、建立測試資料、修正重複扣款
Sub-task把 standard issue 再拆小，可分別描述、指派與估算付款表單、付款失敗測試
Parent／child 是相對關係，不是固定類型名稱。Story 可以是 Epic 的 child，同時又是 subtasks 的 parent。Subtask 在預設最底層，不能再有 child。

不要把 Story 與 Task 排成上下層

預設情況下，Story、Task、Bug 都是同層的 standard types。若「付款」底下要拆成設計、開發、測試三份更小工作，可以用 subtasks。若三件工作都需要各自獨立追蹤，就用 standard issues，再依需求放到同一 Epic。

Premium／Enterprise 可配置額外 hierarchy levels，Advanced Roadmaps／Plans 也會用到；這是官方頁的延伸功能。本節先掌握預設三層，不要為了讀懂 Epic 而先學進階組織規劃。

3．Story、Task、Bug、Subtask：如何選？

需求情境建議類型判斷理由
使用者希望能記住常用收件地址Story描述使用者需要得到的結果。
整理 demo site 測試資料Task一件明確要做的工作，未必需要寫成使用者故事。
地址儲存後消失Bug既有產品行為失常。
「地址管理」牽涉新增、修改、刪除與測試Epic（若是較大交付）可拆成多筆標準工作，整體追蹤成果。
某個 Story 內要分派前端畫面與測試Subtasks是同一筆標準工作內可分工的小塊。
另一團隊需要獨立排程、單獨追蹤的工作通常獨立 standard issue不應只因工作小，就強塞為另一筆工作的 subtask。

這些是教學判斷，不是按字數或工時長度強制決定類型。先問：「它是不是一個更大成果？」「是否要獨立追蹤？」「是不是某筆工作內的分工？」

Subtask 不等於只有 Task 能使用。官方說可以拆分任何 standard issue，包括 Bug、Story 與 Task。Subtasks 可以個別描述與估算；別把 Story 當成最底層，認為再也不能拆。

4．Company-managed：類型建立好，還要配置給 project

建立一種 issue type，和讓某個 project 可以使用它，是兩件事。Issue type scheme 負責將可用的 types 對應到 projects。這也是 620.1.1 講到 shared configuration 時要留意的影響範圍。

概念圖：不是在每個 project 裡輸入同樣的類型名稱，就自動完成共用設定。

  1. 先寫出需求例如：團隊要用 Epic 統整功能、Story 記錄使用者需求、Bug 記錄缺陷、Task 記錄一般工作，以及 Subtask 分工。先使用既有標準類型，避免沒有用途的新類型。
  2. 檢查 project 可用 types以 Jira admin 檢查 company-managed project 的 issue type scheme，確認需要的 types 已包含。若是 shared scheme，先確認還有哪些 projects 使用它。
  3. 建立必要的 sub-task typeJira settings → Work items／Issues → Work types／Issue types 下的 Subtasks，選 Add subtask work type／Add sub-task issue type。輸入 name、description；可在建立時選擇對應 scheme，也能之後再配置。
  4. 驗證使用者看得到在正確的 company-managed 練習 project 打開一筆 Task／Story，從 More actions 找 Create subtask。確認有預期類型、能填資料、建立後顯示在 parent 底下。選項名稱與位置可能依介面不同。
Subtasks 預設啟用。想停用之前，要先將既有 subtasks 轉成 standard issues；不是把開關關掉就可以忽略現有資料。建立、編輯與刪除 sub-task types 是 Jira admin 層級操作，不要把一般 project admin 與 Jira admin 混為一談。

5．有子工作，不代表父工作自動被擋住

假設「付款功能」有「開發付款表單」與「測試付款失敗」兩個 subtasks。你要求測試未完成時不能把 parent 標為完成。這是 workflow transition 的限制，不是單純建立 subtask 就完成的規則。

只建立 Parent／child

表達分工與關聯。

不能因此推定 Jira 一定阻止 parent 轉到 Done。

再加 Subtask Blocking Condition

在 parent 的相關 transition 上加條件。

只允許 subtasks 處於指定狀態時通過。

  1. 找出要被限制的 transition例如 parent 的 Resolve／Done transition。先看完整 workflow，有沒有其他路徑也能到完成狀態；只管一條路可能留下別的入口。
  2. 編輯 workflowJira settings → Work items／Issues → Workflows → 找目標 workflow → Edit。官方 Configure sub-tasks 使用傳統編輯器的 Conditions 路徑；新版編輯器可能以 rules 呈現。
  3. 新增條件選 transition → Conditions → Add condition → Subtask Blocking Condition → Add。選擇允許的 subtask statuses，例如 Done／Resolved，再完成設定；若 workflow 有 draft，依畫面發布後才驗證。
  4. 做正反兩種測試有一筆 subtask 還在進行中時，parent 完成應被阻止；將所有 subtasks 移到允許狀態後，再測 parent 完成應可執行。
Condition 控制「可不可以走這個 transition」，不會替你把 subtasks 自動完成，也不會自動產生 subtasks。官方另提到可用 automation 按條件建立子工作；詳細規則設計在 620.4。
互動實驗 · Workflow condition

試著完成 parent Story

模型假設：已在這條 transition 加入 Subtask Blocking Condition，只接受 Done；其他必要權限均已符合。

Parent Story條件尚未滿足In Progress

先試一次，再完成兩筆 subtasks，重新嘗試 parent transition。

6．維護類型與大量子工作時，注意什麼？

動作／限制官方說明對你的影響
編輯 sub-task type可調整 name、description、avatar名稱是分類辨識，不是 issue 的進度。
刪除 sub-task type官方建議先找出該類型工作，批次改成其他現有類型先處理已有資料，再刪類型；不要把刪類型當成整理 issue 的第一步。
停用 subtasks需先將既有 subtasks 轉成 standard是全域功能的變更，請只在隔離的練習環境理解流程。
單一 parent 超過 500 children目前官方說父項目最多顯示 500 筆 child；更多時改從 search 查看不是第 501 筆一定不能存在；這是顯示／使用限制。
超過 500 children 且使用 time tracking官方指出不能再 include subtasks過度龐大的 parent 應評估拆分，避免追蹤與操作困難。

官方頁面的其他類型，也要認得它們在哪裡

指定的 What are work types? 同時介紹 business 與 service 的 types。Business 預設以 Task 與 Subtask 為主；software 則有 Epic、Story、Task、Bug、Subtask。Jira Service Management 另有 Change、IT help、Incident、New feature、Problem、Service request、Service request with approval、Support，分別服務變更、求助、事故、功能需求、根因調查與服務請求等工作。

這些列在同一篇文件，不代表你應把所有 service types 加進 ACP-620 的 software project。推薦 configuration 時，仍要回到團隊需求與產品情境。

7．Demo site 實作：從一個 Epic 到完成條件

  1. 建立隔離的 company-managed 練習 project名稱「ACP620 Company Lab」，key CMLAB。沿用可用的 software template；檢查 scheme 是否共用。若要改 workflow，使用適合測試的獨立設定。
  2. 建立 Epic 與 standard issuesEpic：「完成訂餐體驗」；Story：「付款成功」；Bug：「修正重複扣款」；Task：「整理測試資料」。將三筆 standard issues 設為這個 Epic 的 children；目前介面可使用 Parent 關係欄位，舊介面可能稱 Epic Link。
  3. 把 Story 拆成兩個 subtasks「完成付款表單」、「驗證付款失敗」。指派給不同的測試成員或自己的測試帳號，分別填入描述與驗收條件。
  4. 口頭檢查層級指出 Story 同時是 Epic 的 child 與 subtasks 的 parent；Bug 與 Task 跟 Story 是同層。
  5. 配置並驗證 blocking condition依前節在 parent workflow 加入條件。讓一筆 subtask 留在 In Progress，測試 parent 被擋住；再全部完成，測試可以通過。
  6. 記錄測試結果至少記錄「subtasks 狀態／走哪條 transition／是否成功」。不要只看 parent 顯示 Done，就認定所有路徑都受到限制。

8．情境題與解析

1．Story 可以同時是 parent 與 child 嗎？

  1. 可以
  2. 不可以，只有 Epic 能當 parent
查看答案與解析

A。Story 可位於 Epic 底下，又有 subtasks。Parent／child 是關係。

English version

1. Can a Story be both a parent and a child?

  1. Yes
  2. No; only an Epic can be a parent
Answer and explanations

Answer: A

A: A Story can belong to an Epic while also having subtasks. Parent and child describe relationships.

B: A standard issue can parent subtasks, so parenthood is not limited to Epics.

2．哪個不屬於預設 standard 層？

  1. Task
  2. Bug
  3. Subtask
查看答案與解析

C。Subtask 在下一層；Story、Task、Bug 才是 standard。

English version

2. Which type is not at the default standard level?

  1. Task
  2. Bug
  3. Subtask
Answer and explanations

Answer: C

A: Task is a standard-level issue type.

B: Bug is a standard-level issue type.

C: A Subtask belongs to the level below standard issues such as Story, Task, and Bug.

3．團隊要求所有 subtasks 完成，parent 才能 Resolve。該做什麼？

  1. 只要建立 subtasks 即可
  2. 在相關 transition 加 Subtask Blocking Condition
  3. 把 issue type 改名 Done
查看答案與解析

B。A 只建立關係，C 混淆類型與狀態。

English version

3. A team requires all subtasks to be complete before the parent can be resolved. What should be configured?

  1. Creating subtasks is sufficient
  2. Add a Subtask Blocking Condition to the relevant transition
  3. Rename the issue type to Done
Answer and explanations

Answer: B

A: The relationship alone does not enforce a transition restriction.

B: The condition enforces the requirement on the relevant parent transition.

C: An issue type’s name is not a workflow status or a blocking condition.

4．要停用 subtasks，但已有使用中的 subtasks，先做什麼？

  1. 直接關閉
  2. 先轉成 standard issue types
查看答案與解析

B。官方明確要求先處理既有 subtasks。

English version

4. Subtasks must be disabled, but existing subtasks are still in use. What should happen first?

  1. Disable them immediately
  2. Convert the existing subtasks to standard issue types
Answer and explanations

Answer: B

A: Existing subtasks must be addressed before disabling the feature.

B: The documented prerequisite is to convert existing subtasks first.

5．Jira admin 建立了新 type，但 project 裡沒有選項，先查什麼？

  1. Issue type scheme 是否包含它
  2. 把 project 改名
查看答案與解析

A。Type 必須透過 scheme 對應到 project；改名與可用類型無關。

English version

5. A Jira admin created a new issue type, but it is not available in a project. What should you check first?

  1. Whether the project’s issue type scheme includes it
  2. Rename the project
Answer and explanations

Answer: A

A: The scheme determines which issue types are associated with the project.

B: A project’s name does not control its available issue types.

6．新增一種名叫 Initiative 的 standard type，就自動比 Epic 高一層嗎？

  1. 是，名稱決定層級
  2. 否，名稱與 hierarchy configuration 是不同事情
查看答案與解析

B。階層要依相應配置，不能靠命名創造一層。

English version

6. Does creating a standard issue type named Initiative automatically place it above Epic?

  1. Yes; the name determines the hierarchy level
  2. No; naming and hierarchy configuration are separate
Answer and explanations

Answer: B

A: A name does not create or assign a higher hierarchy level.

B: The appropriate hierarchy configuration is required; naming alone is insufficient.
