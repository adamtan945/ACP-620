本課沿用考綱的 project／issue／issue type；目前官方介面常稱 space／work item／work type。操作入口可能因導覽更新不同，請依功能名稱對照。練習使用隔離的 demo site；權限與方案限制分開檢查。

把基本設定改對，也知道改了會發生什麼

本節涵蓋 project details、project sidebar／navigation、categories 與移到 Trash。你會用已建立的 TMLAB 與 CMLAB 練習辨認設定；刪除相關練習另用空白 project，避免失去前面累積的練習資料。

完成標準：你能區分 name 與 key、URL 與 Jira 位址、owner／lead 與 assignee；知道 category 不會產生 parent project；能說出 Trash 的 60 天與還原權限。

1．Details 是 project 的基本資料卡

開啟 project，從 Project／Space settings → Details 查看。若沒有直接入口，找名稱旁 ⋯ → Settings。改完按 Save details／Save。不同管理方式、方案與介面可見欄位可能不同，不要把總覽頁列出的欄位當成每個 project 都一定有。

欄位它是什麼修改前先想什麼
Name搜尋、目錄與切換 project 時看到的名稱人們是否能辨認；與 key 是不同欄位。
KeyIssue key 的前綴，如 TMLAB-1 的 TMLAB舊 links、filters、JQL、外部系統是否仍引用它。
URL指向 project 相關外部資訊的網址不會改 Jira 站台或 project 的實際網址；只在 company-managed 提供。
Description描述此 project 做什麼寫目的、範圍、找誰協助；官方說 admin 可在 settings 的 Summary 查看。
Category將相似 projects 分類跨 project 搜尋與篩選；不是權限或階層。
Avatar／Icon代表 project 的圖示幫助辨認，不影響 workflow。
Project lead／Space owner此 project 的負責人欄位不要將 owner 欄位等同完整權限來源。
Default assignee新工作採用預設指派時的接收方式Unassigned 或 owner／lead；還需考慮其他指派機制。
Background／Card covers視覺呈現目前 details 頁有列出，但沒有完整操作教學；依可見的外觀／卡片設定調整。

官方總覽列出較新的 Space owner 名稱；考綱年代常見 Project lead。這裡依該頁功能作對照，不延伸推定所有 Atlassian 產品的 owner／lead 都等義。

不要把通用 Details 清單套到所有管理方式

現行 team-managed 專用文件列出 Name、Key、Category、owner 與 default assignee，並提供 icon 修改步驟。Category 是從 Jira admin 建立的分類中指派；不代表 project admin 可管理全站 category 清單。Description 則不能只因通用 Details 文件提到，就推定 team-managed 的 Details 一定有相同欄位。

反例：題目問 team-managed 可改哪些基本資料，看到 Category 就排除？

不應排除。先區分「建立／刪除全站分類」與「將本 project 指派到既有分類」。前者由 Jira admin 管理，後者現行 team-managed 文件提供 Details 下的操作。讀題要辨認動詞，而不只看欄位名稱。

2．Name 是稱呼，Key 是識別碼的一部分

Name

ACP620 Team Lab
↓ 改名
ACP620 訂餐練習

讓人更容易認出 project。

Key

TMLAB-12
↓ 修改前綴
FOODLAB-12

改變 issue 的識別碼前綴。

官方說改 project name 時，站台 filters 中的名稱會自動更新；改 key 則要特別檢查 board filters、dashboard filter gadgets 與其他 queries。這兩個操作的影響不能混為一談。

  1. 先確認誰可改通用 Edit details 頁寫 organization／site／Jira admins 才可編輯 key；team-managed 專用建立與編輯頁則寫具備 project permissions 者可修改。兩篇官方說明並不完全一致。具備 Jira admin 身分即可進行這項練習；不要把「所有 project admin 一定可改」背成通則。
  2. 填入合法 key至少兩個字元、以大寫英文字母起頭，只能含大寫英文字母與數字。例如 FOODLAB 可用；1FOOD 或 food-lab 不符合規則。
  3. 儲存並查驗改 key 後重新查看一筆 issue。Team-managed 專用頁提醒 board 顯示更新可能需最多 10 分鐘。記錄舊 key 與新 key，不要因短暫未更新就反覆改。
  4. 驗證舊連結與查詢一般舊 issue links 仍可導向新 key，但連結文字不一定會改，例如仍顯示 TMLAB-12。官方建議更新 board filters、dashboard gadgets、global queries；也檢查自己知道的外部整合。
保留 previous key 與刪除 previous key，是兩件事。目前官方會保留舊 key，讓舊 links／filters／queries 繼續工作；也新增刪除 Previous space keys 的操作，讓舊 key 可重新使用。刪掉之後可能破壞那些引用，不要把它當成單純清理歷史。

官方頁面本身有需要一起讀的段落

Edit details 前段說舊 key 仍保留，不能直接拿來建立其他 project；後段另提供刪除 previous key 的方式。完整閱讀後的理解是：沒有移除舊 key 前，不要預期它已釋出。本課保留兩段的條件，避免只背一句絕對結論。

3．Owner／lead、Default assignee 與 URL

假設小雅負責替團隊收件與分派。你可以讓她擔任 project owner／lead，並將 Default assignee 設為 owner／lead；若設定 Unassigned，新工作採用此預設機制時就保持未指派。

Default assignee 不是任選一個姓名的獨立欄位。目前通用官方頁說可選 Unassigned 或 Space owner。要指定另一人，依該機制先更換 owner。若不能用 Unassigned，team-managed 專頁提示檢查全站 Allow unassigned work items／issues。

這是 project 層級的預設行為。手動指定 Assignee、components 或 automation 等可能涉及其他規則；不要將「改 Default assignee」推定為把所有既有 issues 全部重新指派，完整的自動指派邏輯在 620.3.5。

你想做的事正確觀念
讓小雅管理設定確認她的 Administrator role／相應 permissions；不要只改 owner 欄位就假定授權完成。
提供團隊文件入口Company-managed 可在 URL 填完整文件網址；這是外連，不是 Jira base URL。
換 iconDetails → Change icon → 選現有圖示或上傳 → Save details。
把 software 改成 business官方說不能直接切換；需建立目的 project 並搬工作。不要將改 details 當成改管理模型。

Default assignee 不是強制覆寫所有指派

把 owner／lead 設為預設收件人，不代表所有工作永遠派給他。建立時明確選了其他 assignee，或 component 預設、automation 另有設定，都可能影響結果。先看建立時送入的值，再查預設機制與 History；詳見 預設負責人與派工排查。

4．Category：把 projects 分組，不是建立階層

例如把「訂餐前台」「付款服務」「物流整合」歸到 Commerce category，方便在目錄、搜尋、filters 或 reports 中找這組工作。它像資料夾標籤，但不會產生 parent／child project，也不會自動共用 permissions 或 workflows。

  1. Jira admin 建立分類Settings → Spaces／Projects → Space／Project categories，填 name 與 description，按 Add。練習可用「ACP620 Lab」。
  2. 指派給 projectProject settings → Details → Category 選擇分類 → Save details。Company-managed 通用頁建議由 Jira admin 指派；team-managed admin 可從本地 Details 選擇已有分類。
  3. 觀察分類結果在 project 目錄篩選 category，確認兩個練習 projects 被放在一起。這不會合併其 issues。
  4. 理解刪除分類Jira admin 到 Categories 找目標 → Delete。這是在移除分類，不是執行「刪除 category 底下所有 projects」。練習後重新檢查原 projects 仍存在，並查看其 Category 欄位。

5．導覽要讓人找得到工作，不只改外觀

考綱用 project sidebar 一詞；目前官方說明已改以 space／board navigation 的 tabs 操作。核心需求不變：顯示常用入口、安排順序、設定預設 view，並加入相關文件連結。

需求目前官方步驟重要限制／影響
開啟 project 先看到 Board目標 tab → ⋯ → Set as default所有成員開啟時的預設頁；可用 views 依 project 類型與 features 而異。
修改 tab 名稱Tab → ⋯ → Rename → 輸入 → Enter是入口名稱，不是重命名 issues 或 statuses。
重新排序拖動 tabs，或 ⋯ → Move tab left／right改動會讓所有能存取 project 的人看到。
移除入口Tab → ⋯ → Remove不能直接移除 default tab；先另設 default。List 與 Apps tabs 不能移除。
加回入口導覽的 ＋ → 選 tab → Add to navigation移除導覽入口不等於刪除 underlying issues。
增加文件捷徑Shortcuts → 輸入完整網址與名稱 → Add shortcut需 Jira admin 或 project admin；所有有 project 存取的人可看到連結。
編輯／刪除捷徑Shortcuts → Edit shortcut → Update／Remove shortcut移除連結不會刪除連結目的文件，也不會替人取得目的站台權限。

練習：加入名為「訂餐規格」的 demo 文件捷徑，把 Board 設為 default，再以一般帳號重新開啟 project。確認是共用導覽改變，而不是只改你個人的畫面。網址請使用有效的完整 URI，例如 https:// 開頭；顯示連結與能打開文件是不同權限。

6．Trash 是有期限的暫存，不是永久備份

使用中可搜尋與操作
→
Trash保留 60 天，可還原
→
永久刪除不能復原

移到 Trash 時，project 的 issues、components、attachments 與 versions 會一起保留在 Trash；不會因此刪掉仍與其他 projects 共用的 schemes、workflows 或 issue types。

問題官方行為
還能搜尋到 issues 嗎？不會出現在 basic／advanced search results。
直接開舊 issue link 呢？Trash 頁說仍可由 direct link 存取，但不能編輯；不要把隱藏搜尋當成存取控制策略。
誰可以移到 Trash？Jira／site admins 可處理兩種類型；project admin 只能把 team-managed 移到 Trash。
誰可以還原？Jira／site admin；還原專頁明列 Administer Jira global permission。不是有一般 project admin 就一定能還原。
能在 60 天前永久刪除嗎？管理員可提前永久刪除；不能把「60 天」理解成一定能保留滿 60 天。
還原後呢？Project 回到目錄，issues 回到搜尋；官方另提醒原有無效的 legacy epic-link 關係不會被復原。
將工作標為 Done、從 board 清除 Done、移 project 到 Trash、永久刪除，是四種不同動作。題目出現「看不到」時，先確認發生的是哪一種。

三種「不見了」的復原方式不同

情境資料發生什麼事先往哪裡查
卡片被 board filter／clear Done 排除工作仍存在搜尋、board 篩選與完成顯示設定
Version 被 archive版本退出一般選擇清單，歷史關聯保留Releases 的 archived 顯示與原 issue
Project 移到 Trash整個 project 進入有期限的待刪狀態Jira admin 的 Trash 與還原期限

這三種動作不是同義詞。不要用刪除 project 來修理 board 上的顯示，也不要以為 archived version 會把相關工作轉成 Done。

封存整個 project：保留紀錄，但退出一般搜尋

Project／space Archive 與移到 Trash 不同。現行 Jira 的 project 封存適用 Premium、Enterprise；工作退出基本與進階搜尋，仍可依原有權限透過直接連結讀取，但不能編輯。封存不會刪掉共用 schemes 或 workflows，也不是撤銷資料存取權的方法。

Jira／site admin 可封存與還原 company-managed、team-managed projects；project／space admin 的此項權限限 team-managed。需要長期保留舊專案但減少搜尋干擾，可評估 Archive；若仍要讓外包團隊持續編輯，就不符合封存後唯讀的行為。參考 官方封存說明。

互動實驗 · Project lifecycle

同一個 project，三種不同狀態

使用中→Trash→永久刪除
使用中：會出現在目錄與搜尋；能否編輯仍依使用者權限。

這是純前端示範。真實 Jira 的永久刪除不能靠「重設」救回；admin 也可能在 60 天前提前永久刪除。

7．Demo site 實作：修改、驗證，再還原

  1. 練 Name 與 URL在 CMLAB 修改名稱，填一個 demo 文件 URL、description 與 icon。重新進目錄確認；觀察 URL 沒有把 Jira 的網址改掉。
  2. 練 Category建立 ACP620 Lab category，分配給 TMLAB、CMLAB，在目錄確認分組。一般帳號仍依原有 permissions 存取，不因 category 獲得權限。
  3. 練 Key（選做）先保留一個練習 issue 的舊 link，再修改練習 project key，確認新 key 與舊 link 導向。不要刪 Previous keys；這裡只驗證改名後的相容行為。
  4. 練導覽由 admin 改 default view、加入 shortcut，一般帳號重新開啟，確認看到相同導覽；若無法打開 shortcut，檢查目的文件權限。
  5. 另外建立 Trash 練習 project名稱 ACP620 Trash Lab。先建一筆測試 Task，複製 direct link，並記錄可搜尋到。不要使用 TMLAB／CMLAB 做永久刪除練習。
  6. 移到 Trash以 Jira admin：Settings → Projects／Spaces（或 Manage spaces）→ 找目標 → ⋯ → Move to trash → 確認 Move。先讀清楚確認視窗的 project 名稱。
  7. 驗證三件事一般搜尋找不到；direct link 依權限與官方行為可讀但不能編輯；admin 在 Trash 看得到移除者、移除時間與預計永久刪除日期。
  8. 立即還原以 Jira admin：Settings → Projects／Spaces → Trash → 找目標 → Restore。確認回到目錄、搜尋到 issue，原測試資料仍在。永久刪除只理解後果，這輪不需要操作。

8．情境題與解析

1．修改 Project URL，是否會改掉 Jira site 的網址？

  1. 會
  2. 不會，它是相關資訊的外部連結
查看答案與解析

B。URL 是目錄中的外連欄位，不能當成站台網址設定。

English version

1. Does changing Project URL change the address of the Jira site?

  1. Yes
  2. No; it is an external link to related information
Answer and explanations

Answer: B

A: The Project URL field is not the site-address setting.

B: It provides an external reference in project information rather than changing the Jira site URL.

2．把兩個 projects 放到同一 Category，會自動共用 permissions 嗎？

  1. 會
  2. 不會
查看答案與解析

B。分類只是組織與查找，不是 shared configuration，也不是 parent project。

English version

2. Do two projects in the same Category automatically share permissions?

  1. Yes
  2. No
Answer and explanations

Answer: B

A: Categorization does not establish shared permission configuration.

B: A Category organizes and helps find projects; it is neither shared configuration nor a parent project.

3．改 key 後，舊 link 文字沒變，是否一定失效？

  1. 是
  2. 否，保留舊 key 時仍可導向新 key
查看答案與解析

B。顯示文字與連結導向是不同事；刪除 Previous keys 又是另一個風險。

English version

3. After a project key changes, an old link’s displayed text remains unchanged. Must the link be broken?

  1. Yes
  2. No; retained previous keys can still redirect to the new key
Answer and explanations

Answer: B

A: Visible link text and link resolution are different things.

B: Previous keys can preserve redirection. Removing Previous keys is a separate risk.

4．一般 project admin 能還原 company-managed project 嗎？

  1. 只要曾管理那個 project 就可以
  2. 需要 Jira／site admin 等符合還原要求的權限
查看答案與解析

B。還原不是一般 project admin 的預設權力。

English version

4. Can an ordinary project admin restore a company-managed project?

  1. Yes, provided they once administered that project
  2. Restoration requires the applicable Jira or site administration permissions
Answer and explanations

Answer: B

A: Past project administration does not automatically grant restoration authority.

B: Restoring a company-managed project is not a default power of an ordinary project admin.

5．Project 移到 Trash，相關共用 workflow 會一起永久刪除嗎？

  1. 會
  2. 不會因移到 Trash 而刪除共用設定
查看答案與解析

B。其他使用共用設定的 projects 不應因此失去設定。

English version

5. When a project moves to Trash, is its shared workflow permanently deleted too?

  1. Yes
  2. No; moving the project to Trash does not delete shared configuration
Answer and explanations

Answer: B

A: Other projects may still depend on that configuration.

B: Trashing one project does not remove shared configuration used elsewhere.

6．為什麼無法移除某個 navigation tab？

  1. 可能它是 default，或是不能移除的 List／Apps
  2. 因為所有 tabs 永遠不能變動
查看答案與解析

A。先檢查 tab 的角色與類型；必要時先換 default。

English version

6. Why might a navigation tab be impossible to remove?

  1. It may be the default tab, or a non-removable List or Apps tab
  2. No tabs can ever be changed
Answer and explanations

Answer: A

A: Check the tab’s role and type; changing the default may be necessary before removing an eligible tab.

B: The restriction is not a universal prohibition on all navigation changes.

7．Trash 中滿 60 天後，可隨時還原嗎？

  1. 可以
  2. 不可以，期滿會永久刪除
查看答案與解析

B。Trash 不是無限期備份，管理員也可提早永久刪除。

English version

7. Can a project be restored at any time after spending 60 days in Trash?

  1. Yes
  2. No; it is permanently deleted when the retention period expires
Answer and explanations

Answer: B

A: Trash is not an unlimited backup.

B: The retention period is finite, and an administrator can also permanently delete a project earlier.
