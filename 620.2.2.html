LESSON 620.2.2 · BOARD CONFIGURATION

配置跨團隊、跨 project 的 board

用 saved filter 彙整共同工作，同時保留各 project 的歸屬、workflow 與權限。

考綱沿用 project／issue／issue type／rule；現行文件可能稱 space／work item／work type／flow。依功能辨認入口；先確認管理方式、權限與方案。下列互動均為本機模擬，實作步驟只供隔離的 demo site 跟做。

考綱目標：Given business requirements, configure boards across multiple teams and projects

一塊共同板，不是把 projects 合併

訂餐平台的網站組使用 WEBLAB，API 組使用 APILAB。產品負責人想一次看兩邊的交付進度，卻不想搬移 issue 或重設權限。適合建立跨 project board：搜尋條件選到兩個 project，columns 對齊共同流程，swimlanes 再按 project 區分。

建立跨 project board 的四個決定

決定如何配置不會自動發生的事
資料範圍Saved filter：project in (WEBLAB, APILAB) ORDER BY Rank ASC。若只要共同計畫，可再加既有 label 或其他條件。不會把 APILAB 的 issue 搬到 WEBLAB。
板型與 location選 Scrum 或 Kanban；Location 可選合適 company-managed software project 或個人 profile。Location 不會取代 filter；放在 WEBLAB 不代表只讀 WEBLAB。
流程呈現把兩邊實際 statuses 映射到相應 columns，讓 Developing、Implementing 同屬 Doing。映射不會替 project 建立原本不存在的 workflow transition。
存取與責任分享 saved filter 給目標群組／角色，確認各 project 的 Browse 與 issue security，指定 board 管理人。分享 filter 不會授予 issue 的閱讀或編輯權限。

跨團隊不一定跨 project：同一 project 可用 component 或 label 分出不同板；跨 project 也不一定要一塊共享操作板，有時只需要 dashboard，見 620.5.2。當團隊節奏不同，一塊共同 Kanban 概覽與各自的 Scrum board 可以共存，但必須知道它們讀取同一資料。

跨 project 的五個連動

同一張卡片：在共同板移動卡片會改原 issue status，在其他板也會反映；它不是可任意試改的副本。

不同使用者看到不同總數：filter 定義共同候選資料，實際可讀項目仍依使用者權限。Board admin 不等於每個來源 project 的 admin。查看與操作權限見 620.3.1。

不同 workflow：同一 column 可收多個 status，但每張卡片只能沿自己 workflow 的合法 transition 移動。不要因 API 組不能拖到 Review，就假設是瀏覽器故障。

共同 sprint：跨 project Scrum board 的 sprint 管理必須查所有相關 project 的 Manage Sprints 權限，不能只看 location project。尤其寬廣或複雜 filter 可能擴大需檢查的範圍；遇到無法開始／完成 sprint，先縮明資料範圍、再查權限。

估算與報表：兩組應先對齊估算欄位與意義。8 story points 不應和 8 hours 當成同一數字加總；共同板的報表反映共同範圍，不能直接當作某一組的績效。

Team-managed 的內建板設定留在自己的 project。若要額外或跨 project board，官方目前提供從 saved filter 建立 company-managed board 的方式；這不會把來源 project 轉成 company-managed，也不會讓兩種估算欄位自動統一。

管理板的人可在 Board settings 的 Administrators 指定使用者或群組；板管理權與 saved filter 的管理權應分別安排。刪 board 只移除視圖，issue 仍屬於原 project；若要清理練習板，不必連 issue 一起刪除。

Sprint 權限名稱核對：目前官方 company-managed 權限清單仍列 Manage sprints，說明涵蓋建立、開始、完成及調整 sprint；建立 sprint 的操作頁也以此為主要權限。本次查閱未找到名為 Create and Reorder Sprints 的獨立 permission。不要把「建立與重新排序 sprint」這段操作描述直接當成權限名稱；重新排序 sprint 與排序 sprint 裡的 issue 也不同，後者還涉及 Schedule／Edit 與 Rank。若特定站台顯示新名稱，應再以該站台權限說明核對，而非只憑舊題選項。官方：Space access and configuration permissions。

跨 project 可以共用視圖，但不能抹去資料邊界

動作可行性與要查的條件容易誤判之處
把另一 project 的 standard issue 加到 Epic同屬 company-managed 的來源與目標可建立跨 project parent 關係；先確認可讀與可編輯所需權限。Board 顯示在一起不等於把 issue 移至 Epic 的 project；team-managed 與 company-managed 的 parent 邊界另查。
把 issue 指派給另一 project 的版本Version 屬於其 project；不能因跨 project board 顯示版本就直接跨 project 使用。兩個同名版本也不是同一個 version。需要協調發版時在各 project 管理各自版本。
重排跨 project 工作Rank 可讓共同 backlog 形成順序；使用者須能讀取並具有欲移動 issue 所屬 project 的 Schedule 與 Edit 權限。能看板、是 board admin，不代表可以重排所有來源 project 的工作。
反例：把共同板 location 換成 APILAB，會讓 WEBLAB 的版本也能用嗎？

不會。Location 只改板放在哪裡，filter 才決定資料集合，版本仍依 issue 所屬 project。這三層不能互相代替。

搬 location 與改 filter 是兩件事

Board settings → General → Location 可更換板的掛載位置，通常立即生效；原 project 或使用者停用時，也可重新指派 location 讓板方便存取。若需求是「只看 API 工作」，應改 board filter；若需求是「讓大家在產品 project 的 sidebar 找到共同板」，才是調整 location。

改 shared saved filter 前先確認哪些 board、dashboard 或訂閱使用它。只想讓一塊板改範圍時，先 Save as 建新 filter 再讓該板使用；不應直接縮小所有板共用的 filter。

Copy board：新板仍使用同一個 filter

由 All boards 找到來源板，使用 More actions → Copy，可建立板的副本。官方目前明確說明：副本使用與原板相同的 saved filter，執行複製的人會是新板的 administrator；若 filter 不是你建立或你沒有其編輯權限，仍可能無法修改它。想讓副本有獨立資料範圍，需另存新 filter，再指定給副本。

但目前這篇官方主文沒有完整列出副本的 Administrators 名單，也沒有明說原板管理員會保留或移除。因此不能把「複製者是管理員」推成「只有複製者」，也不在此僅憑題庫斷言必定包含全部原管理員。實作驗證請比較複製前後 Board settings → Administrators 的使用者與群組，再分別檢查 filter 權限。官方：Copy an existing board（2026-09-08 核對）。

複製板的檢查清單：比較「新舊板的 Saved Filter 是否同一 ID」「誰能編輯該 filter」「Administrators 中的使用者與群組」。沿用同一 filter 表示之後改查詢會同時波及兩板；不能把 Copy board 當成 Copy filter。官方主文只確認複製者成為管理員，沒有完整名單證據時，避免將「只有複製者」或「所有原管理員必保留」寫成絕對規則。

Demo lab：兩個 project、一塊 board

  1. 使用兩個獨立測試 company-managed projects WEBLAB、APILAB，各建一筆 Task。記下真實 key 與 status，替換以下範例。
  2. 進階搜尋執行 project in (WEBLAB, APILAB) ORDER BY Rank ASC；預期至少找到上述兩筆。另存新 filter，分享給指定測試成員，避免公開分享。
  3. 從 saved filter 建立 Kanban board「ACP620 Cross Lab」，Location 選 WEBLAB 或自己的 profile。
  4. Columns 檢查兩筆工作的 status 均已映射。Swimlanes 選 Projects／Spaces；預期卡片按 project 分成不同橫列。
  5. 在有兩邊 Browse 權限的測試帳號查看，應見兩筆；若有既有只讀一邊的測試帳號，用它比對應只見可讀項目。沒有第二帳號時記為未驗證，勿宣稱權限測試通過。
  6. 將 location 換成自己的 profile，重新開板。預期 filter、issue key、所屬 project 不變。

驗收：你能用實際 key 證明 location 與來源分離；能區分 filter share 和 Browse 權限。保留測試配置，不需改動任何正式 project 權限。

五題跨 project 情境

以下皆為原創單選情境題，非官方考古題。先選答案，再展開解析；每題只有一個最佳答案。

1．共同板掛在 WEBLAB，filter 包含 WEBLAB、APILAB。卡片來源為何？

  1. 只有 WEBLAB
  2. 兩者中使用者可讀且符合條件的 issue
  3. 全部自動搬至 WEBLAB
  4. 由 swimlane 名稱決定
查看答案與四個選項解析

答案：B

A：Location 不是來源條件。

B：Filter 與個別權限共同決定可見資料。

C：建立板不會搬 issue。

D：Swimlane 只是呈現分組。

English version

A board is located in WEBLAB and its filter includes WEBLAB and APILAB. Which issues can it show?

  1. Only WEBLAB
  2. Matching issues from both projects that the viewer can access
  3. All issues are moved to WEBLAB
  4. The swimlane name determines the source
Answer and explanations

Answer: B

A: Location is not the source query.

B: The filter and the viewer’s access together determine visible data.

C: Creating a board does not move issues.

D: Swimlanes organize the display.

2．同事能開共同板但看不到 API 工作，優先查什麼？

  1. 增加 Card colors
  2. 把 board 改名
  3. APILAB 的 Browse 與 issue security
  4. 刪除 APILAB
查看答案與四個選項解析

答案：C

A：顏色不授權。

B：名稱不改權限。

C：先查使用者是否能直接讀取缺少的 issue。

D：刪除會破壞資料且不解決權限。

English version

A colleague can open the board but cannot see API work. What should you check first?

  1. Add card colors
  2. Rename the board
  3. Browse access and issue security in APILAB
  4. Delete APILAB
Answer and explanations

Answer: C

A: Colors do not grant access.

B: Names do not change permissions.

C: First confirm that the viewer can directly read the missing issue.

D: Deletion destroys data and does not solve access.

3．只想改一塊板的範圍，共用 filter 已被三塊板使用，較適合？

  1. Save as 新 filter，讓目標板使用
  2. 直接覆寫原 filter
  3. 搬 location
  4. 改所有 issue 的 project
查看答案與四個選項解析

答案：A

A：能保留其他視圖既有範圍。

B：會波及依賴同 filter 的板。

C：位置不改查詢。

D：移動資料過度且可能改配置。

English version

Three boards share a filter. Only one board needs a different scope. What is suitable?

  1. Save a new filter and select it for the target board
  2. Overwrite the shared filter
  3. Move the board location
  4. Move every issue to another project
Answer and explanations

Answer: A

A: This preserves the scope used by the other views.

B: This affects boards that depend on the shared filter.

C: Location does not change the query.

D: Moving issues is excessive and may change their configuration.

4．跨 project status 分別叫 Developing、Implementing，想同欄呈現？

  1. 統一刪除 statuses
  2. 建立兩份 issue
  3. 只改卡片顏色
  4. 兩個 status 映射到同一 column
查看答案與四個選項解析

答案：D

A：刪 status 不是必要步驟。

B：複製會產生資料分歧。

C：顏色不能合併欄位。

D：多對一映射保留原流程並統一呈現。

English version

Developing and Implementing should appear in one column. What should you do?

  1. Delete the statuses
  2. Duplicate the issues
  3. Only change card colors
  4. Map both statuses to the same column
Answer and explanations

Answer: D

A: Deleting statuses is unnecessary.

B: Copies would create divergent data.

C: Colors do not combine columns.

D: Many-to-one mapping preserves the original workflows while unifying their display.

5．Team-managed project 想要額外跨 project board，何者正確？

  1. 只能轉管理方式
  2. 使用 saved filter 建 company-managed board
  3. 新增板會自動共享 workflow
  4. 一定要改為 Scrum
查看答案與四個選項解析

答案：B

A：目前有額外板的 saved filter 路徑。

B：官方提供這條路徑，來源 project 管理方式不變。

C：Board 不會共享或轉換 workflow。

D：可依工作需求選 Scrum 或 Kanban。

English version

A team-managed project needs an additional cross-project board. Which statement is correct?

  1. It must change its management type
  2. Create a company-managed board using a saved filter
  3. A new board automatically shares workflows
  4. It must switch to Scrum
Answer and explanations

Answer: B

A: The saved-filter route provides an additional-board option.

B: This is the documented route; the source project keeps its management type.

C: Boards do not convert or share workflows automatically.

D: Scrum or Kanban can be chosen according to the need.
