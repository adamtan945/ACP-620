考綱目標：Troubleshoot board and filter configurations

搜尋找得到，不代表板一定看得到

同事說「API-12 不見了」，這不是足夠精確的故障描述。先取得 key，確認哪位使用者、哪塊板、哪個視圖、何時開始發生。用同一位使用者驗證，才能避免 admin 看得到就判定所有人都正常。

依序縮小問題，而非同時亂改

症狀先查如何確認
使用者連 issue 都開不了Browse、issue security、產品存取。以該使用者直接開 key；不能讀時先處理存取，詳見 620.3.1。
能開 key、不能開 boardSaved filter 是否分享給該使用者；板是否仍有有效 location。確認 base filter 能開與 board 的 Saved Filter 名稱。
Search 找得到、board 無卡實際 saved filter、Kanban sub-filter、status mapping。使用相同使用者查 filter，逐層加條件比對 key。
Scrum backlog 有、Active sprints 無是否在目前 active sprint。查 Sprint 欄與該板 sprint；planned sprint 不等於 active。
一開某 quick filter 卡片就消失多個 quick filters 的交集、currentUser()、內建篩選。全部清除後一次啟用一個，記錄集合。
卡片在錯欄或完成量不對Status-to-column mapping、最右完成欄。開 issue 看真實 status，對照 Columns。
有卡片但不能拖順序ORDER BY Rank ASC、Edit Issues、Schedule Issues 與必要存取；Rank 是欄位，並非權限名稱。不要只查 Browse；排序與讀取是不同能力。
不能跨欄移動Workflow transition、conditions、validators 與權限。開 issue 的 status 選單看合法動作，不靠新增 column 繞過。

顯示問題與操作問題分開診斷。板的 quick filter 是視圖條件，不是安全邊界；藏住卡片不等於對方不能從搜尋開啟它。

先把「管理 Sprint」和「改 Sprint 的工作」拆開

想做的事主要權限／配置不要誤認
建立、開始、完成 sprint，改期間或 goalManage sprints；跨 project 時查相關來源範圍。Schedule + Edit 不能完整代替 Manage sprints。
把工作加進／移出 sprint，重排工作依動作檢查 Schedule work items、Edit work items、Rank 啟用；Browse 是讀取前提。有 Manage sprints 不代表可修改每一張 issue。
設定 board columns 或 quick filtersBoard admin 或 location project／space admin 的設定權；另查 filter 編輯權。Board admin 不是所有來源 project 動作權的捷徑。

新建空 sprint 與把 issue 放入 sprint 是不同操作；「能建立但不能加入工作」不矛盾。跨 project 排錯要拿一筆可操作與一筆不可操作的 key 比較所屬 project 權限，不要只授予 location project 的權限就結案。

Rank 為何會影響拖曳排序？

需求「讓 product owner 手動決定 backlog 優先順序」通常應使用 ORDER BY Rank ASC。若板以 ORDER BY priority DESC 排序，畫面主要按 Priority 排，不能把它當作自由手動排序。Rank 是 Jira 的全域排序欄位，不要另建一個同名自訂欄位。

Board 的 Add Rank 會更新 saved filter，使用該 filter 的其他板也會受影響。同一批 issue 在不同板共享 Rank，某板的重排可能反映到另一塊以 Rank 排序的板。這是共同資料，不是每塊板獨立一份優先順序。

修正時先另存測試 filter，以 project = BDLAB ORDER BY Rank ASC 驗證。在需要調整正式共用 filter 前，先理解使用者依賴的排序意圖；若既要依 priority 查看又要手動排程，可以用不同視圖達成，不必把兩者混為一種排序。

權限足夠，仍要確認這種工作是否支援該視圖

Company-managed Scrum backlog 不把 subtask 列為可獨立規劃的工作，因此不能把它當成普通 Story 在此清單自由排序。需要獨立排優先順序或加入不同交付規劃時，先評估是否應改成標準工作；不要為此追加 Jira admin 權限。這項限制不能套用成「所有看板的子工作永遠不能排序」，也不能把父工作詳細頁的子工作順序，與 Scrum backlog 的獨立 Rank 混為一談。參考 Scrum backlog 顯示條件。

自訂 quick filters 疊加的常見陷阱

想要「我的 Bug」，同時開 Mine 與 Bugs 是合理的交集。想要「Bug 或 Task」，同時開 Bugs 與 Tasks 則可能變成互斥條件：一筆 issue 不會同時是這兩種類型。正確做法是單一 quick filter 寫 issuetype in (Bug, Task)。

內建 Assignee picker 一次選兩人，通常表達這兩人任一；不可把「同一 picker 多個值」與「兩個自訂 quick filters」視為相同邏輯。現行官方配置主文未逐項說明所有新版控制項的組合，遇到新版介面時用下面四筆資料驗證，不從按鈕名稱猜測。

檢查題：Mine 有 A、B；Bugs 有 B、C；Tasks 有 A、D。Mine + Bugs？Bugs + Tasks？

Mine + Bugs 剩 B；Bugs + Tasks 是空集合。若要 B、C、A、D 的聯集，改寫單一 OR／IN 條件。這個教材模型針對自訂 quick filters，並非所有畫面 picker 的通用規則。

一個完整案例：已發版 Bug 為何消失？

使用者可開 BDLAB-12，base filter 也選得到；status Closed 映射於最右欄。這三項只能排除部分原因，還沒排除 Kanban sub-filter。若 sub-filter 只保留 unreleasedVersions 或 EMPTY，而這張 Bug 唯一 Fix version 剛 Released，就可能被排除。

處理方式是先確認這是否符合板的工作流設計。若板本來只顯示尚未交付範圍，消失可能是正常結果；需要回顧版本則去 release 頁或適當報表。若確實想保留歷史，才調整測試板 sub-filter，評估資料量。不要把版本改回 Unreleased 只為了讓卡片重現，這會改變真實交付資料。

「五週後隱藏」不是內建五週選項

Company-managed Kanban 的 Hide completed work 目前官方列出 1、2、4 週或不隱藏；不要捏造內建 5 weeks。若需求是自訂五週，可考慮適當 JQL，但先問五週以什麼事件起算。

例如在支援該欄位的測試板以 statusCategory != Done OR updated >= -5w，代表保留非 Done-category 工作，以及最近五週有更新的工作。它是「依最後更新」的範例，不是「完成後精確五週」；若用 resolutiondate，則必須確認 workflow 有正確設定與清除 Resolution。另檢查內建 1／2／4 週隱藏是否仍更早排除工作，避免兩層條件互相矛盾。

官方指出，Hide completed work 的完成計時會因欄位編輯而重設；已完成很久的 issue 今天改了 Description，可能重新出現。這不是 issue 自動重開，也不能只因重現就修改它的 status 或 version。

最近一週與本曆週，是不同需求

Hide completed work 設為 1 week，不能解讀成「只顯示本週解決的工作」。例如週三回看最近七天，仍可能包含上週的工作；而內建隱藏計時還受欄位更新影響。若需求明確是本曆週的解決紀錄，應以 resolved >= startOfWeek() 等日期條件設計查詢，並確認時區、週起點及 Resolution 的設定。若要保留未完成工作，還要明確加入它們的條件；不要直接用只查已解決工作的 filter 取代整張工作板。日期邊界例子見 620.5.1。

Demo lab：建立最小故障並復原

  1. 在獨立測試板準備我的 Bug、我的 Task、其他人 Bug、其他人 Task 四筆工作，記下 key；無第二使用者時用未指派替代，前提是站台允許。
  2. 先確保 base filter 選到四筆、status 已映射且無額外 sub-filter 排除。記下「正常基線」四筆清單。
  3. 新增 Bugs、Tasks 兩個自訂 quick filters，先分別啟用確認各兩筆，再同時啟用，觀察互斥；清除後四筆恢復。若新版顯示不同，記錄控制項種類與實測，不硬套結論。
  4. 只在專用 board 將一個使用中的 status 移到 Unmapped。預期 key 可直接開、saved filter 可找到，但板少了卡片。重新映射即可復原。
  5. 將專用 filter 改成 ORDER BY priority DESC，觀察排列；回復 ORDER BY Rank ASC，驗證可依權限拖曳排序。不要修改多板共用的正式 filter。
  6. 逐項核對回復後 filter、mapping、quick filter 狀態與四筆基線相符。將每個故障對應到一個排除層，避免同時改多項。

驗收：你能在不改 issue 真實業務資料的情況下解釋並修正兩種「消失」，且知道 Rank 排序與 transition 是兩個問題。

五題故障定位

以下皆為原創單選情境題，非官方考古題。先選答案，再展開解析；每題只有一個最佳答案。

1．使用者可開 issue、base filter 可找到，但板無卡，下一步？

  1. 重新建立 issue
  2. 查 sub-filter、mapping 與目前視圖
  3. 直接授 Jira admin
  4. 刪除 project
查看答案與四個選項解析

答案：B

A：會造成重複資料。

B：已排除直接閱讀與 base，繼續下一層。

C：過度授權不定位原因。

D：破壞資料且不相關。

English version

A user can open an issue and the base filter finds it, but the board does not show it. What is next?

  1. Recreate the issue
  2. Check sub-filter, mapping, and current view
  3. Grant Jira admin immediately
  4. Delete the project
Answer and explanations

Answer: B

A: This may create duplicate data.

B: Direct access and base matching are established; inspect subsequent layers.

C: Excessive access does not locate the cause.

D: Deletion is destructive and unrelated.

2．想手動拖 backlog 順序，適合的排序？

  1. ORDER BY created DESC
  2. ORDER BY priority DESC
  3. ORDER BY Rank ASC
  4. 依 card color
查看答案與四個選項解析

答案：C

A：按建立時間。

B：按優先級，不是自由 Rank 次序。

C：對應手動排序與相關排程能力。

D：顏色不是 JQL 排序欄。

English version

Which ordering fits manual backlog ranking?

  1. ORDER BY created DESC
  2. ORDER BY priority DESC
  3. ORDER BY Rank ASC
  4. Card color
Answer and explanations

Answer: C

A: This sorts by creation time.

B: This sorts by priority rather than free Rank order.

C: This supports manual ranking and related planning actions.

D: Card color is not the relevant JQL sorting field.

3．分享 saved filter 是否足以讓對方讀所有匹配 issue？

  1. 否，仍受各 issue 權限約束
  2. 是，分享就授 admin
  3. 只要板公開就全部可讀
  4. 只看 working days
查看答案與四個選項解析

答案：A

A：查詢存取與資料存取分開。

B：分享不是管理權授予。

C：Board 可見不繞過 issue security。

D：日曆與資料授權無關。

English version

Is sharing a saved filter sufficient to read every matching issue?

  1. No; issue permissions still apply
  2. Yes; sharing grants admin
  3. A public board exposes everything
  4. Only working days matter
Answer and explanations

Answer: A

A: Query access and data access are separate.

B: Sharing is not a grant of administration.

C: Board access does not bypass issue security.

D: Calendar settings do not authorize data access.

4．Bugs 與 Tasks 自訂 quick filters 同開變空，原因？

  1. 所有資料被刪
  2. Workflow 壞掉
  3. 瀏覽器語言不同
  4. 互斥類型條件取交集
查看答案與四個選項解析

答案：D

A：清除 filter 可恢復視圖。

B：與 workflow 不一定相關。

C：語言不改類型交集。

D：需要任一類型時用單一 IN／OR 查詢。

English version

Separate Bugs and Tasks custom quick filters produce no results when both are enabled. Why?

  1. All data was deleted
  2. The workflow is broken
  3. Browser languages differ
  4. Mutually exclusive type conditions are intersected
Answer and explanations

Answer: D

A: Clearing filters can restore the view.

B: A workflow problem is not implied.

C: Language does not change the intersection.

D: Use one IN or OR query when either type should match.

5．Add Rank 的影響範圍？

  1. 只有自己的螢幕
  2. 使用同一 saved filter 的其他板也受影響
  3. 只改卡片顏色
  4. 建立新 project
查看答案與四個選項解析

答案：B

A：會修改共用 filter。

B：應先評估 filter 相依關係。

C：Rank 是排序，不是顏色。

D：不會建立 project。

English version

What can Add Rank affect?

  1. Only the current screen
  2. Other boards using the same saved filter
  3. Only card colors
  4. It creates a project
Answer and explanations

Answer: B

A: It changes the shared filter.

B: Assess filter dependencies before changing it.

C: Rank controls ordering, not color.

D: It does not create a project.
