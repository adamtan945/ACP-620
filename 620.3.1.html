LESSON 620.3.1 · MANAGING PROJECTS

辨認權限層級，組合出可用的操作

能登入不代表能看，能看不代表能改；先辨認權限作用範圍，再檢查完成一項操作需要哪些條件。

考綱沿用 project／issue／issue type／rule；現行文件可能稱 space／work item／work type／flow。依功能辨認入口；先確認管理方式、權限與方案。下列互動均為本機模擬，實作步驟只供隔離的 demo site 跟做。

考綱目標：Determine appropriate permissions for project team members (project, global)

本課目標與案例

訂餐網站團隊有開發者、顧問與管理者。顧問只需閱讀與留言；開發者要修改工作與登錄工時；小組長要管理 sprint。你要用最少且足夠的權限滿足工作，不把所有人都設為 Jira admin。本課以 company-managed project 的 permission scheme 為主；team-managed 的 access 與角色疊加請先讀 620.1.2。

先分清楚四種問題

Global permissions 是全站能力，例如批次修改功能；project permissions 是某 project 內的能力；issue security 在已有 project 存取之上再限制特定 issue。它們不是一張可互相替代的通行證。分享 filter 只分享查詢，不會把查詢結果的資料權限送給收件者。

Permission scheme 可以授予 project role、group 或指定使用者等對象。角色名稱本身沒有魔法：把人放進 Developers，只有 scheme 真正授予 Developers 的權限才會生效。多條授權路徑通常是加總；移除一個角色，不會抵銷另一個群組給的權限。

不要把第一道關卡讀成所有人一定要付費 Jira 授權：現行權限文件列出 Browse Projects 等部分能力可授予已有 site access、沒有 Jira app access 的使用者；Create Issues 也有不先取得 Browse 的例外。一般團隊工作仍應逐項確認產品、站台與操作條件，不用一個絕對句取代權限表。

Global permissions 由 Jira admin 管理並授予 groups。Project admin 通常無法在自己的 project 設定頁把全站 Bulk change 權限加給人；應把需求與使用者群組提供給 Jira admin。

目前文件還可能列出 Manage versions、Manage Work Item Layouts、Edit workflows、Archive／Restore Work Items 等新增權限。考綱題目沿用較早名稱；實際操作以站台可見項目為準，別用固定權限總數作答。

Administer Projects 讓管理者處理本 project 的角色成員、components、versions 等設定；不等於能自由修改全站共用 scheme、任意建立 global custom field，或忽略 issue security。共享設定應交由 Jira admin 評估影響。

補充權限功能與界線
View aggregated data查看 board、backlog、deployment 的彙總洞察；即使個別工作受限，也可能呈現數量、Epic 名稱等彙總資訊，需分開評估。
View (read-only) workflow查看 workflow 圖，不是編輯 workflow 或執行 transition。
Edit workflows現行細分權限可在新 workflow editor 編輯非共用流程；共用配置仍需 Administer Jira。
Manage work item layouts調整既有欄位的 layout；不授予建立全站新欄位的能力，共用配置另受限制。
Archive／Restore work items封存及還原工作各自授權；與 Delete 的不可還原資料移除不同。

Delete Issues 會刪除 issue 及其附屬資料，即使操作者沒有個別的 Delete all comments／attachments；但它不授權單獨刪除某則留言或某個附件。Resolve Issues 另涉及 Resolution 與 Fix version 的可用性，不能只把它當作「能移動到某個叫 Done 的欄位」。

診斷演練：Ben 有 Edit Issues，卻完全看不到一張 issue。先查什麼？

先查 Browse Projects、issue security 與產品存取，確認 issue 的確存在且網址正確。Edit 是操作能力，不能取代可見性。若直接網址能開但 board 找不到，才轉查 board filter、sub-filter、columns。詳見 620.2.7。

現行官方的重疊權限規則：上述組合以 permission scheme 已設定相應專屬權限為常見前提。How permissions interact 指出，若 scheme 只定義 Edit Issues、完全未配置 Assign Issues，Edit 可包含 Assignee 編輯；配置 Assign Issues 後，專屬限制優先，只有被授予 Assign 的人可改。只有 Assign、沒有 Edit 的人也能只改 Assignee。排錯要讀實際 scheme 與 workflow，不把「沒有 Edit」一律推論成「任何欄位都不能改」。

相同 project，也可能只有部分 issue 能轉移

Permission scheme 不只授權固定 group／project role，也可授權 Current assignee、Reporter、User custom field value 等由每張 issue 決定的對象。例如 Transition Issues 只授予 Current assignee，Amy 是 ACLAB-1 的 assignee，卻不是 ACLAB-2 的 assignee；即使兩張工作同屬 ACLAB、共用同一 scheme，她的轉移資格仍可能不同。還要各自檢查 workflow condition、validator、目前狀態與 issue security。

因此跨 project 操作要逐 project 檢查，批次或跨 board 操作也要逐 issue 檢查。不要把「這個 project 有一張成功」推論成「此 project 全部一定成功」，也不要把同一 project 的部分失敗一律當成資料損壞。來源：Grant or revoke permissions in a scheme。

把操作條件拆成可驗證的反例

Create Issues 不要求先有 Browse Projects；因此「成功建立，但之後無法打開自己建立的工作」可能是權限設計的結果。Reporter 身分也不會自動給 Browse，除非方案另外把可見性授予 Reporter。新增成功不能用來證明閱讀或編輯權限完整。

改一般描述查 Edit；改 Reporter 另查 Modify Reporter；改 Assignee 查 Assign，候選人查 Assignable User。Resolve Issues 還涉及 Resolution 與 Fix version，實際填寫仍受 screen、workflow 及其他必要權限限制。遇到特殊欄位不能改時，先讀本節的重疊權限規則，再核對該欄位，避免只補 Edit 而漏掉專屬限制。

讀權限表：先列需求，再找角色聯集

例如測試人員只需查看工作、登錄工時與切換狀態。先列出 Browse Projects、Work on Issues、Transition Issues；若要從敏捷 board 操作，另外檢查產品存取與 filter 分享。再逐列查哪些群組或角色提供這些能力，選足夠且不額外授予管理權的組合。登錄工時不等於修改既有 worklog，因此不要把 Edit All Worklogs 當成必要條件；在欄間移動狀態也不等於跨 project 的 Move Issues。

只有當 permission scheme 的 Browse Projects 明確授予 Application access 時，對應產品存取才會透過該列提供 Browse；不能推廣成所有 project 都會如此。角色名稱本身不保證權限，應讀實際 scheme，並另外檢查 workflow conditions、validators 與 issue security。

批次改 Components：權限之外還有欄位條件

Make bulk changes 是全站入口；Edit Issues 必須涵蓋每一筆選取工作。官方 bulk edit 條件另要求這批工作屬於同一 project、該 project 已有 components，而且欄位未在相關 field configurations 隱藏。工作已 resolved 並不把修改 Components 變成 Resolve Issues 操作；仍須檢查工作目前可否編輯。參考 官方批次欄位條件表。

Demo lab：用一般帳號驗證權限

  1. 在 demo site 使用專門的 company-managed project（例如 ACLAB），準備管理者及已有 Jira 存取的一般測試帳號。若方案不提供 permission scheme 編輯，用閱讀與預測表完成演練；GitHub 免費與 Jira 方案是兩件事。
  2. 由 Jira admin 複製一份測試用 permission scheme，只套用 ACLAB；記錄原 scheme，避免動到其他 project。先讓測試角色具有 Browse Projects、Add Comments，建立一張普通 Task。
  3. 管理者到 Project settings → People／Access，把測試帳號加入該角色。使用另一個瀏覽器工作階段登入測試帳號。預期能開 issue、能留言，不能編輯 Summary。
  4. 加上 Edit Issues 後重整，用同一帳號更新 Summary。預期編輯成功；接著檢查 Due date，若 scheme 明確將 Schedule Issues 限定授予管理者、未授予測試帳號，不能因 Edit 成功就宣稱排程也可用。
  5. 指派測試前分別確認操作者 Assign Issues、目標 Assignable User。記錄「操作／授權路徑／結果」，不要只截管理者看到的設定頁。
  6. 移除本次新增測試成員，還原測試 scheme 的變更；若帳號仍可看 project，列出其他 group／role／直接授權路徑。

情境練習：每個選項都要能解釋

題目 1．Sam 能批次修改 A，卻不能批次修改 B；最合理的下一步？

  1. 重裝瀏覽器
  2. 檢查 B 的 Edit Issues 與資料可見性
  3. 再給一次 Make bulk changes
  4. 把 B 的 board 改名
查看答案與逐項解析

答案 B。A 沒有指向授權差異；B 檢查每個 project 的必要條件；C 既已在 A 使用批次功能，就不是先重複給同一全域權限；D 名稱不影響 issue 權限。

English version

Sam can bulk edit in A but not B. What should you check next?

  1. Reinstall the browser
  2. Check Edit Issues and visibility in B
  3. Grant Make bulk changes again
  4. Rename B’s board

B. A does not explain a project-specific difference. B checks the required local permissions. C repeats a global capability already demonstrated in A. D does not change access.

題目 2．希望別人能把工作指派給 Eva，Eva 最直接需要哪項？

  1. Assign Issues
  2. Manage Sprints
  3. Assignable User
  4. Share filters
查看答案與逐項解析

答案 C。A 是執行指派的人需要；B 管 sprint；C 定義可被指派資格，仍需合理存取；D 是分享查詢。

English version

Which permission most directly allows Eva to be selected as an assignee?

  1. Assign Issues
  2. Manage Sprints
  3. Assignable User
  4. Share filters

C. A is for the person performing the assignment. B manages sprints. C makes Eva an eligible assignee, subject to access requirements. D shares searches.

題目 3．Project admin 要改共用 permission scheme，應如何處理？

  1. 直接編輯一定只影響自己 project
  2. 找 Jira admin 評估共用範圍並修改或複製
  3. 把自己設為 assignee
  4. 新增 quick filter
查看答案與逐項解析

答案 B。A 忽略共享 scheme 的影響與管理權；B 是正確管理邊界；C 只改工作負責人；D 只改 board 篩選。

English version

A project admin needs a shared permission scheme changed. What is appropriate?

  1. Edit it because only this project is affected
  2. Ask a Jira admin to assess shared usage and edit or copy it
  3. Become the assignee
  4. Add a quick filter

B. A ignores shared impact and administration boundaries. B handles both. C changes issue ownership only. D filters a board.

題目 4．Filter 已分享，同事看到空結果，何者正確？

  1. 分享一定失敗
  2. 分享不保證 Browse Projects 或 issue security 存取
  3. 必須有 Administer Jira 才能搜尋
  4. 把所有 issue 設 Done 即可
查看答案與逐項解析

答案 B。A 太早下結論；B 分清查詢存取與資料存取；C 過度授權；D 狀態與資料授權無關。

English version

A shared filter returns no results for a colleague. Which statement is correct?

  1. Sharing must have failed
  2. Sharing does not grant Browse Projects or issue security access
  3. Only Jira admins can search
  4. Set all issues to Done

B. A is premature. B separates filter access from data access. C overstates required privileges. D does not grant access.

題目 5．移除 Developers 角色後仍能編輯，最合理原因？

  1. Jira 永遠保留所有舊權限
  2. 另一群組仍授予 Edit Issues
  3. 只有 site admin 能編輯
  4. 角色是拒絕清單
查看答案與逐項解析

答案 B。A 不正確，應檢查現存授權；B 符合多路徑加總；C 與一般使用者能力矛盾；D 角色不是 deny。

English version

A user can still edit after removal from Developers. Why?

  1. Jira retains all old permissions forever
  2. Another group grants Edit Issues
  3. Only site admins can edit
  4. Roles are deny lists

B. A is false; investigate current grants. B matches additive access paths. C is false. D confuses membership with denial.
