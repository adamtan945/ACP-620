LESSON 620.3.3 · MANAGING PROJECTS

用 versions、releases 與 Timeline 看交付

Version 表示這次交付包含什麼，Timeline 表示什麼時候做；範圍一變，預測與報表也會跟著改。

考綱目標：Implement versioning, manage releases and roadmaps, and predict the impact of scope changes

先定義交付，才有進度可談

訂餐網站預計推出「1.0 線上付款」。包含付款頁、交易 API、失敗重試三筆工作。把三筆的 Fix versions 設為 1.0，就能從同一個版本查看交付範圍；Bug 的 Affects versions 則表示問題出現在哪些舊版本。兩個欄位都選 1.0，語意也不同。

Version 的狀態與管理

設定／動作意義影響
Fix versions預定在哪一版修好或交付決定 issue 屬於哪次 release
Affects versions哪些已存在版本受問題影響不把 issue 加入該版交付範圍
Unreleased尚未發布的版本過了 release date 可顯示逾期
Released版本被標示已發布影響版本選單、報表與部分 board 顯示；不自動等於每張 issue Done
Archived隱藏不用的歷史版本可 Unarchive，與刪除不同
Merge將某版本合入另一版本原本關聯的工作轉至目標版本
Delete刪除版本定義確認工作要改掛其他版本或移除引用
重新排序調整版本列表順序與修改實際 release date 是不同的變更

建立或修改版本可從 Releases／Versions → Create version 或 ⋯ → Edit。日期是規劃值，不是自動替所有工作排程；Version Report 可用 start date 更貼近真正開工時間。較舊考綱以 project admin 管版本，現行權限頁另有 Manage versions (releases) 的細分授權。

Team-managed 的兩種版本欄位不可混推：啟用 Releases 可使用 Fix versions，不代表 Affects versions 也同時可用。Affects Version/s 的官方功能請求在 2026-09-08 查核仍為 Gathering Interest。新增一個同名文字欄位並不會取得系統版本欄位的語意與關聯。

Release hub：進度與可交付性要一起看

打開 Releases → 選版本。先看範圍與完成狀態，再看 warnings。若開發工具已連接、工作 key 出現在 branch／commit／pull request，且使用者有 View Development Tools，就能對照開發證據。

訊號應該問什麼
Issue Done，PR 還開著工作流程是否提前標完成？還有 review 或合併要做？
Issue Done，build failed這個版本真的可交付嗎？失敗的 pipeline 是否相關？
尚未 review 的 commits團隊的 review 政策是否已落實？
Deployment 成功部署到 testing 還是 production？成功部署不等於全部 release 範圍已驗收。
Related work 連結／placeholder發布說明、設計、分析或支援文件是否已準備？

考綱指定 Related work：將發布檢核所需的外部工作連結集中在版本頁，例如 Confluence 發布說明與設計文件；它不是另一個 Fix versions，也不會把外部文件變成 Jira issue。2026-09-07 指定 URL 主文仍提 related work 狀態，但舊 Add links 章節已不在回傳主文；入口依站台 rollout 顯示，不能只靠舊錨點找按鈕。

Release 時確認日期及 unresolved 工作要保留、移到下一版本等可用選項。單純按 Release 不等於把每筆 issue 轉成 Done。現行版本頁還有 approvers／Require approvals 等新功能，應與 2023 考綱核心分開；也不應把 Jira 的 Released 一律當作程式已部署到 production。

完整情境：1.0 準備發布，未完成工作改掛 Fix version=1.1；之後發現 1.0 的問題，可在新 Bug 記錄 Affects version=1.0、Fix version=1.1。Released 描述交付狀態，並不使版本不能再被引用。Archive 也不會凍結 issue 的編輯或等同 Delete。若把草稿版本合入 1.1，合併會移除來源版本；不要把 Merge 理解成保留兩個獨立版本並同步它們。

Roadmap 的目前名稱是 Timeline

考綱寫 project roadmap，現行官方文章以 Timeline 說明。它以甘特圖呈現單一 project 的長期工作，通常從 Epic 與其 child issues 看起。這跟跨 project 的 Plans（舊稱 Advanced Roadmaps，Premium／Enterprise）不同。

Timeline 元件讀法與操作
左側階層Epic／parent 與 child work；可從側欄開 issue 修改內容
時間長條Parent 依設定日期或 child 日期推算；Kanban child 使用 Start date／Due date
Scrum child可使用 sprint 日期或工作 Start date／Due date；缺 parent 的 child 不會出現在此階層
Weeks／Months／Quarters切換觀看尺度，不是把 issue 工期自動換算成不同承諾
Dependencies顯示 blocks 等工作相依，不保證自動改期或阻擋 transition
Filters可暫時隱藏部分工作；不改原本 Fix versions 或 parent 關係

「跨三個 projects 排同一張長期計畫」不能只靠單一 project Timeline。先評估 Plans；「同一 project 的付款 Epic 看不到 child」則先查 parent、日期與 filters，不用立刻升級方案。

跨 project 的 Epic／parent 關係與 version 的範圍要分開。Company-managed 的工作可在支援的關係與權限下連到其他 project 的 Epic，但各 project 的同名「1.1」仍是不同 version，不會因共用 Epic 就變成同一份 release 清單。單一 project Timeline 的顯示範圍也不等於 parent 關係允許的全部範圍。

Plans：先模擬容量，再決定是否寫回

Plans 可依團隊 capacity 與 velocity 規劃交付，並用 scenarios 比較不同安排。例如同一批跨團隊工作，可比較「維持人力」與「調整交付範圍」兩種計畫。計畫內的變更需經 review／save 才寫回 Jira 工作；模擬中的日期不是已向團隊正式承諾的日期。

判斷功能時，優先找具體能力，例如容量規劃、相依性與多情境比較。「Portfolio」或「Lean」等廣泛用語本身不足以判定全部支援或全部不支援，也不能直接推論有預算與投資管理功能。參考 官方 Plans 功能入口。

Scope changes：完成量一樣，進度也可能下降

假設這版最初 20 points，已完成 10，簡化進度是 50%。新增 10 points 的工作後，完成量仍是 10，總範圍成了 30，比例變成約 33%。這不代表團隊把已完成工作撤回，而是分母變了。報表還可能因未估點、估算重改、board filter 或狀態映射產生差異。

先預測：Burnup 完成線不動、scope 線上升，最先查什麼？

查是否新增工作、把既有工作納入 sprint／version，或提高估算。這是範圍變大；不能只憑兩條線的距離直接判定成員效率下降。

報表範圍變動如何讀
Sprint Report檢查 sprint 開始後新增／移出的工作，以及未完成工作去向
Burnup完成量與總 scope 分開，新增 scope 可讓總量線上升
Burndown剩餘工作受新增、移除與重新估算影響，不只受完成影響
Version Report／Release Burndown預測依 scope、估算與歷史進度調整；不是保證發布日期
Kanban board常用 sub-filter 可能排除 released versions，發版後卡片消失不等於被刪

詳細解讀與報表選擇見 620.5.3；版本條件如何影響 board 見 620.2.4。

Demo lab：做一次可追蹤的版本變更

  1. 在隔離 company-managed project 建立 Lab 1.0 與 Lab 1.1。填開始日、預計發布日；不接 production 發布 pipeline。
  2. 建立三張 Task，Fix versions 設 Lab 1.0；另建 Bug，只把 Affects versions 設 Lab 1.0。預期 release 範圍是前三張，Bug 不因 Affects 自動加入。
  3. 建立一個付款 Epic，把前三張 Task 加為 children。開 Timeline 設日期，切換 Weeks／Months；確認關係與日期呈現。
  4. 完成其中一張 Task，記錄 release progress；再把另一張新 Task 納入 Lab 1.0。預期完成張數不變、總範圍增加。
  5. 在不連 production 工具的測試版本上試 Release，仔細確認未完成工作的處理選項，必要時移到 Lab 1.1。檢查原 issue 狀態，不把版本標示當成 transition。
  6. 試 Unrelease／Archive／Unarchive 並觀察版本選單。刪除與 Merge 先用額外空白版本練習；結束後保留必要紀錄、清掉本次測試資料。

情境練習

題目 1．Bug 在 1.0 發生，預計 1.1 修好，欄位怎麼填？

  1. Affects 1.1、Fix 1.0
  2. Affects 1.0、Fix 1.1
  3. 只要 Labels=1.1
  4. 兩欄都不可多選
查看答案與逐項解析

答案 B。A 把影響版與修復版反轉；B 正確；C 不能取代 release membership；D 這些欄位可記錄多個版本，不是題目障礙。

English version

A bug affects 1.0 and will be fixed in 1.1. Which values are correct?

  1. Affects 1.1, Fix 1.0
  2. Affects 1.0, Fix 1.1
  3. Only Labels=1.1
  4. Neither field allows multiple values

B. A reverses the meanings. B is correct. C does not establish release membership. D is false and not the issue here.

題目 2．按 Release 後 issue 仍 In Progress，何者合理？

  1. 版本發布不自動把所有 issue 完成
  2. Jira 必定損壞
  3. 必須刪除此 issue
  4. Affects versions 一定錯
查看答案與逐項解析

答案 A。B 過早下結論；C 不合理；D 不足以解釋 status。應檢查 release 時未完成工作的處理選擇。

English version

An issue remains In Progress after a version is released. What explains this?

  1. Releasing a version does not automatically complete every issue
  2. Jira must be broken
  3. Delete the issue
  4. Affects versions must be wrong

A. B is premature. C is inappropriate. D does not explain status. Check the chosen handling of unresolved work when releasing.

題目 3．想跨四個 projects 排長期計畫，選哪個？

  1. 單一 project Timeline 一定全部涵蓋
  2. 評估 Plans 與方案
  3. 只換 Timeline 顏色
  4. 把 Done 改名 Released
查看答案與逐項解析

答案 B。A 超過單一 Timeline 範圍；B 對應跨團隊規劃；C、D 無法提供跨 project 計畫。

English version

Which approach supports long-term planning across four projects?

  1. One project Timeline always includes all of them
  2. Evaluate Plans and its plan requirements
  3. Change Timeline colors
  4. Rename Done to Released

B. A exceeds a single-project Timeline’s scope. B addresses cross-project planning. C and D do not.

題目 4．Scope 從 20 增加為 30，完成量仍 10，何者正確？

  1. 完成量倒退
  2. 進度比例降低不代表完成工作消失
  3. 速度一定歸零
  4. 應隱藏新工作才能保持真實
查看答案與逐項解析

答案 B。A 混淆比例與數量；B 正確；C 無此推論；D 隱藏會扭曲資訊，應揭露 scope 變更。

English version

Scope rises from 20 to 30 while completed work remains 10. What is true?

  1. Completed work went backwards
  2. A lower completion percentage does not mean work disappeared
  3. Velocity must be zero
  4. Hide the new work to preserve accuracy

B. A confuses ratio and quantity. B is correct. C does not follow. D obscures the scope change.

題目 5．想保留歷史版本但從選單隱藏，首選？

  1. Delete 所有 issues
  2. Archive version
  3. 刪 permission scheme
  4. 把 release date 清空
查看答案與逐項解析

答案 B。A 破壞資料；B 為可還原的封存；C 無關；D 改日期不是封存。

English version

How can you retain a historical version while hiding it from selection?

  1. Delete all issues
  2. Archive the version
  3. Delete the permission scheme
  4. Clear the release date

B. A destroys data. B is reversible archiving. C is unrelated. D does not archive anything.
