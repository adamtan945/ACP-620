LESSON 620.3.6 · MANAGING PROJECTS

設定 issue field layout，分清呈現與權限

把重要欄位放對位置能改善使用；但藏起來、必填與禁止修改，是三種不同設定。

考綱沿用 project／issue／issue type／rule；現行文件可能稱 space／work item／work type／flow。依功能辨認入口；先確認管理方式、權限與方案。下列互動均為本機模擬，實作步驟只供隔離的 demo site 跟做。

考綱目標：Configure issue field layout

欄位在畫面上不見了，可能是哪一層？

客服說 Bug 缺少重現步驟；開發者說 Due date 看得到卻不能改；管理者說把機密欄位放 Hidden 就安全。這三件事不能全靠拖拉 layout 解決。本課建立一條從欄位定義到畫面與權限的檢查路徑。

欄位的五層模型

設定處理什麼常見負責人
Custom field／context資料型別、選項與適用範圍Company-managed 的 Jira admin
Field configuration必填、隱藏及部分呈現行為Jira admin
ScreenCreate／Edit／View／transition 可用的欄位與 tabsJira admin；新細分權限有受限委派
Issue layoutDescription／Context／Hidden 的排列Project admin 或目前授權的 layout 管理者
Permission schemeEdit、Assign、Schedule、Modify Reporter 等操作權Jira admin 配置；project admin 管角色成員

Screen 是可供這種操作使用的欄位集合，layout 是開啟 issue 後的排列。若 Create screen 沒有欄位，單改 View layout 不保證建立時就能填；若 context 排除這個 issue type，layout 也不能憑空帶入它。

Description、Context 與 Hidden

區域適合放什麼行為
Description fields重現步驟、驗收條件、Environment 等較長內容通常左側或單欄畫面上方；多個 screen tabs 也可能呈現在此
Context fieldsAssignee、Priority、Components 等分類資料通常右側；重要欄位置於 hide when empty 線上
Hide when empty 線下偶爾才填的背景欄位空值時在 More fields；有值後顯示到 Details
Hidden fields此工作檢視不需要顯示的欄位從此 layout 隱藏，不等於資料刪除或安全保護
Pinned fields個人最常用的 context 欄位個人快速存取偏好，不是全團隊新的 permission scheme

如果 Task 與 Sub-task 共用同一個 View screen，配置可能以同一組 issue types 一起生效。修改前看清楚正在調整哪個 screen／哪一組 types。Layouts 屬於個別 project；可複製到用相同 screen 的其他 project，但複製不是日後自動同步共享。

  1. 開一張目標 issue，找 Configure → Work item view／Issue layout；不同 rollout 可能位於側欄或 ⋯ 選單。
  2. 將重要 Description／Context 欄位移到適當位置，調整 hide when empty 分界。
  3. 若清單沒有需要的欄位，先查 context、field configuration 與 screen，而不是新增同名欄位。
  4. Save changes，重新開另一張同型別 issue 與另一個共用 screen 的 type，驗證影響。

舊 board issue detail view 與現行完整 work item layout 不要混讀。舊預設 details 的 Summary、Description 不能從預設 layout 刪除；Description 是否隱藏仍受 field configuration 影響。「固定出現在預設配置」也不等於能越過 Edit 權限修改。遇到題目問能移除哪些欄位，先辨認它說的是 board details、完整工作頁，還是 screen。

Team-managed：必填、預設與排序是三件事

Team-managed 管理者可在 Project／Space settings → Issue types／Work types，為該工作類型的欄位勾選 Required；Summary 本來就是必填。欄位的預設內容或預設值則是建立時的起始資料，不是強制使用者永遠保留該值。新版也可能把欄位編輯放在 Space settings → Fields。

原創例：Bug 必須填「重現步驟」，可以設定該欄位必填；提供填寫範本則屬於預設內容。調整 Description fields 的順序只是呈現，不會替任何欄位設定必填。判斷能否拖移某欄位時，要看目前區域、固定欄位與可放置位置，不能把某個只有兩個欄位的舊畫面推成所有 layout 的永久限制。

來源：Customize work item fields in team-managed spaces（2026-09-08 核對）。

2026-09-08 文件差異：team-managed 的 transition screen。舊教材常說完全不支援；但現行 Map a screen to a workflow transition 已列出 team-managed 的 Space settings → Work types → Edit workflow 入口，以及 Request input → Show a screen 操作。這與舊限制不同。實作時確認本站 workflow editor 是否提供該功能及所需權限；本教材未在你的站台實測，不把文件入口當成每個 rollout 都已可用的證明。

預設欄位：名稱、預設值、必填與顯示各自判斷

某個系統欄位不能改名稱，不代表它不能有 default value。較舊 team-managed UI 的 Story point estimate 可提供 Default number，但名稱鎖定；Description 的舊提示也曾禁止更改必填及移除。現行官方已描述在 Work types 對可用欄位勾選 Required，卻未逐一承諾每個預設欄位都提供相同控制。因此應檢查目標欄位實際選項，不能從一般 Required 說明推成 Description 必定可改，也不能把舊截圖當成現在永遠不能改的證明。

估算 default value 只是建立時的起始資料，不是團隊已討論完成的估算。若大量工作都保留同一預設點數，仍需確認估算是否有效。

Layout 不是欄位安全邊界

把「內部成本」放到 Hidden，僅表示此 issue view 不呈現它；不能因此保證 JQL、匯出、其他畫面或 API 都無法讀取。要限制敏感資料，先評估 issue security（限制整張 issue）與真正具備欄位權限能力的設計，不能以視覺隱藏代替授權。

欄位／需求要檢查的權限
一般 Summary／DescriptionBrowse 與 Edit Issues，及 workflow 是否允許編輯
AssigneeAssign Issues；被選的人要 Assignable User
ReporterModify Reporter；並視操作檢查 Edit
Due date／RankSchedule Issues，且編輯／排序需其他必要條件
Security levelSet Issue Security，且安全方案與可用 levels 已配置
Time tracking／Log workWork On Issues；欄位已供應並可使用

現行 Jira 有 Manage work item layouts 的細分權限，只能使用既有欄位，並有未共用 screen 等限制；不把它理解成全站 custom field 管理權。舊題目講 project admin 配 layout，仍需認清 underlying screen 與全站配置的界線。

辨識錯誤設計：把薪資欄位移到 Hidden，只讓 HR 知道欄位名稱，就安全了？

不成立。Layout 是呈現設定，不是欄位存取控制。即使一般畫面不顯示，其他讀取管道仍可能看得到。應重新設計資料存取範圍，並用低權限帳號驗證真正授權。

現行官方的重疊權限規則：上述組合以 permission scheme 已設定相應專屬權限為常見前提。How permissions interact 指出，若 scheme 只定義 Edit Issues、完全未配置 Assign Issues，Edit 可包含 Assignee 編輯；配置 Assign Issues 後，專屬限制優先，只有被授予 Assign 的人可改。只有 Assign、沒有 Edit 的人也能只改 Assignee。排錯要讀實際 scheme 與 workflow，不把「沒有 Edit」一律推論成「任何欄位都不能改」。

以症狀選下一個檢查

症狀檢查順序
只有空白的欄位沒顯示先展開 More fields，再看 hide when empty
Configuration 清單找不到欄位Context → field configuration → relevant screen
View 能看，Create 不能填檢查 Create operation 對應的 screen
看得到 Assignee 但不能修改查 Assign Issues、目標 Assignable User，不先調版面
改 Task 卻影響 Bug檢查是否共用 View screen 與 layout type grouping
另一 project 沒跟著變Layout 是 project 層設定，複製不等於共享同步
所有欄位突然不能改查 Edit Issues、workflow 編輯限制與目前狀態

與 board card layout／issue detail view 的差異：board 的卡片欄位是看板摘要，完整 issue layout 是工作本身的顯示配置；改一個不代表另一個全同步。對照 620.2.6。

Demo lab：觀察空欄位與權限的不同

  1. 在測試 company-managed project 使用一份隔離 screen，選一張 Bug，先記錄原 layout 與 screen 使用的 issue types。
  2. 將 Description 放主要區域、Priority 放 Context 上方、Labels 放 hide when empty 下方。將 Labels 清空後重開，預期需展開 More fields；填值後應出現。
  3. 選一個非敏感測試欄位放 Hidden，再查看原資料仍存在；這只驗證 layout 行為，不能當成安全測試成功。
  4. 以一般測試帳號打開同 issue；若 scheme 已將 Schedule 明確授予管理者，而測試帳號有 Edit 但無 Schedule，檢查 Due date 修改。預期權限不足不因 layout 顯示而解除。
  5. 檢查共用 View screen 的另一 issue type，確認是否一同變動。若要新增欄位，由 Jira admin 只在隔離 screen/context 操作。
  6. 還原 layout 與欄位值，記錄每次結果屬於呈現、screen 或 permission 哪一層。

題目 1．空白欄位不見，填值後出現，最可能？

  1. Hide when empty
  2. Issue 被刪除
  3. 失去帳號
  4. 自動新增 scheme

答案 A。A 正是空值收合行為；B、C 無法解釋填值後出現；D 無此自動規則。

English version

An empty field is hidden but appears once populated. What is likely?

  1. Hide when empty
  2. The issue was deleted
  3. The account was lost
  4. A scheme was automatically created

A. This is the intended empty-field behavior. B and C do not explain appearance after entry. D is not a rule.

題目 2．View 顯示欄位，Create 沒有，先查？

  1. Create screen
  2. Project avatar
  3. Watcher 名單
  4. Sprint goal
查看答案與逐項解析

答案 A。A 決定建立操作的欄位；B、C、D 不控制此畫面供應。

English version

A field appears in View but not Create. What should you inspect?

  1. The Create screen
  2. The project avatar
  3. Watchers
  4. The sprint goal

A. A supplies fields for the create operation. B, C and D do not control that screen.

題目 3．把機密欄位移到 Hidden，就安全嗎？

  1. 是，所有 API 都會隱藏
  2. 否，layout 不是安全邊界
  3. 是，只要改名
  4. 只要開 quick filter 就安全
查看答案與逐項解析

答案 B。A 把呈現誤當授權；B 正確；C 改名不限制存取；D 篩選也不是授權。

English version

Does putting a confidential field in Hidden make it secure?

  1. Yes, every API hides it
  2. No, layout is not an access-control boundary
  3. Yes, if renamed
  4. A quick filter makes it secure

B. A mistakes presentation for authorization. B is correct. C does not restrict access. D filters data without securing it.

題目 4．改 Task layout 同時影響 Sub-task，可能原因？

  1. 兩者用相同 View screen
  2. 所有 project 永遠共用 layout
  3. Sub-task 沒有欄位
  4. 權限永遠失效
查看答案與逐項解析

答案 A。A 符合同組 layout；B 誤稱全站共享；C 錯誤；D 沒有證據。

English version

Why could a Task layout change affect Sub-tasks too?

  1. They share the same View screen
  2. All projects always share layouts
  3. Sub-tasks have no fields
  4. Permissions always fail

A. A explains grouped configuration. B incorrectly assumes global sharing. C is false. D is unsupported.

題目 5．欄位看得到，卻不能改 assignee，先查？

  1. Assign Issues 與 Assignable User
  2. 背景圖
  3. 是否把欄位置左邊
  4. 是否收藏 issue
查看答案與逐項解析

答案 A。A 分別檢查操作者與目標；B、C、D 是呈現或個人操作，不能補足授權。

English version

The Assignee field is visible but cannot be changed. What should you check?

  1. Assign Issues and Assignable User
  2. The background image
  3. Whether the field is on the left
  4. Whether the issue is starred

A. A checks actor and target eligibility. B, C and D do not grant assignment permissions.
