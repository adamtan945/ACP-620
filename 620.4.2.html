LESSON 620.4.2 · AUTOMATION

把業務需求組成 automation rule

從小而明確的觸發條件開始，理解每一步正在處理哪張issue，再用smart values把資料帶到正確的位置。

考綱目標：Create an automation rule based on business requirements

1．把需求拆成事件、條件、對象與動作

需求：「demo project新建Bug，而且Priority是High、還沒有Assignee時，加上needs-triage標籤。」這是最小可驗證的規則。先把要做的事固定，不一次加入通知、跨project搬移與複雜分支。完成後再擴充成指派或關聯工作更新。

Trigger是何時開始；Condition決定是否繼續；Action做改變。Branch不是必備零件，只有需要改到相關對象時才加入。規則現稱flow、步驟可能現稱step，概念仍一致。

2．選正確trigger，避免抓錯事件

業務事件適合trigger容易搞錯
新建工作Issue created啟用之後不會自動補跑所有既有卡
Priority被修改Field value changed，指定Priority不用所有Issue updated事件再逐一篩
某張卡進DoneIssue transitioned，指定目的status狀態轉換應用transition trigger
有人新增留言Issue commented編輯既有留言是不同事件
有人手動要求執行Manual trigger from issue適合demo與隨選動作；可限定允許群組
每天檢查到期未完成工作Scheduled + JQL有無JQL決定是否對搜尋結果逐張執行
版本正式ReleaseVersion released版本事件不等於目前一定有單張issue情境
外部系統通知Incoming webhook需設定URL／secret並確認payload；不是一般網頁連結

Scheduled若加JQL，後續actions對匹配issues執行；若只是要產生一次彙整，常用不逐張觸發的排程配合Lookup issues，再處理回傳清單。不要把每張issue寄一次與整份摘要寄一次混在一起。JQL語法見 620.5.1。

3．Condition檢查資料；If/else選路徑；Branch換對象

零件用途原創例子
Issue fields condition不寫JQL就檢查常見欄位Priority equals High
JQL condition目前issue是否符合queryproject = FOOD AND issuetype = Bug
Smart values condition比較動態值、字串或正規表示式比較觸發留言作者與Reporter
Related issues condition檢查關聯工作存在或符合條件所有sub-tasks是否Done
If/else block依條件選不同動作路徑High加urgent；其他加normal-review
Branch / related issues對關聯issues逐一執行動作逐張sub-task加follow-up標籤

一般condition不符合，後面的動作不執行；這通常是規則正確地排除不符資料。If/else則能走替代路徑。Related issues condition只檢查相關工作，不會自動把action作用對象換成它們；要改那些工作需branch。

現行Related issues branch有巢狀與If/else使用限制；不要把「If/else可巢狀」套用成「任何branch裡都可任意巢狀」。設計先保持簡單，並依實際可加入的step與官方限制確認。

4．Actions：新增、多值欄位與轉換有不同語意

Action怎麼用先核對
Edit issue設定或複製欄位值欄位是否在context／screen中，型別是否正確
Assign issue指定人、輪派、平衡工作量等Actor可Assign；目標可Assignable；範圍與自動指派規則
Transition issue經workflow轉到指定status有可用transition、條件、validator、必填欄位
Create issue／sub-task建立新工作目的project及type存在；Actor有Create與Browse
Comment on issue加動態說明留言對象與可見範圍；避免反覆留言
Log action把測試值寫入audit log適合先驗證；不需真的寄信
Re-fetch issue data取得後續步驟需要的最新issue欄位不是所有每一步都必須加，依資料相依需求
Lookup issuesJQL取得最多100筆清單供smart values使用回傳清單不會自動讓下一個Edit逐張改它們

Labels與多選欄位的預設設定可能取代原有值。只想新增needs-triage時，在Labels選More actions → Add/remove values。其他多選欄位依支援的保留／Copy from issue配置，先在demo驗證。這是「覆寫」與「加到既有集合」的差異，不是語法外觀而已。

Clone會建立新issue，並不是保留所有歷史與關聯的完整複製：狀態回到目的workflow起點、Resolution清空，comments與links不會全部自動複製。建立之後主路徑仍以觸發issue為對象；若要留言到新卡，使用created issues branch。

5．Smart values：動態資料，不是普通字串

Issue: {{issue.key}}
Summary: {{issue.summary}}
Status: {{issue.status.name}}
Assignee: {{issue.assignee.displayName|"Unassigned"}}
Source: {{triggerIssue.key}}

雙大括號表示求值，點號沿物件取屬性。例如issue.assignee.displayName是「這張工作→負責人→顯示名稱」。缺少值通常回傳空字串；可設fallback避免訊息只剩空白。不要把{{issue.status}}當作狀態名稱，明確取.name。

需求寫法說明
輸出目前卡key{{issue.key}}隨branch中的目前對象變化
保留最初觸發卡key{{triggerIssue.key}}在related branch中仍指向來源
列出Lookup清單key{{#lookupIssues}}{{key}} {{/}}#與結尾區段用於格式化清單，不等於批次Edit action
Priority變更前後{{fieldChange.fromString}} → {{fieldChange.toString}}配合相應field-change trigger情境
最後建立的issue{{createdIssue.key}}讀取新卡key，不會改變主路徑action對象
日期運算{{now.plusDays(3)}}是smart value函式；不是JQL的now()
字串轉換{{issue.summary.toLowerCase()}}先確認欄位有值與輸出用途

先用Manual trigger + Log action測試，再把值放進修改或通知步驟。一般JQL與smart values是不同語法；scheduled query中的project = FOOD不是{{project}}。若使用custom field，名稱可能重複或變動，查實際欄位識別碼，不從另一站台照抄ID。

6．Branch內的issue換成誰？

在sub-task branch內，{{issue.key}}是該sub-task，{{triggerIssue.key}}仍是原parent。若把來源與目的寫反，可能複製回錯誤值或留言到錯誤對象。跨project related issue還需要multi-project／global scope與各處actor權限，見 620.4.3。

多筆branch會平行處理，不保證先跑FOOD-11再FOOD-12；主路徑也不應假設所有branches已完成。branch變數隔離，不能把其中建立的變數當成全部分支彙整結果。若只是判斷所有sub-tasks已完成，先使用Related issues condition，不要為了檢查而製造一堆有副作用的branches。

互動推理：Create issue之後直接Comment，留言加在哪？

仍加在trigger issue。想留言到剛建立的卡，進All created issues branch後再Comment。{{createdIssue.key}}只是一個資料值，和「切換action上下文」是兩回事。

互動推理：在每個sub-task分支把counter加1，主路徑讀counter能得到正確總數嗎？

不能把branches當作順序共享記憶體。它們平行且隔離；使用可查得的集合與.size，或重新設計彙整步驟。

7．建立與發布規則：把設定說清楚

Project／Space settings → Automation → Create rule／Create flow → From scratch。選Issue created，再加Bug、High、Assignee empty條件與Add label動作。可從template起步，但每個預填條件與對象仍要核對。

Details／Settings建議練習值意思
NameACP620 High Bug Triage Lab讓audit log可辨識
Description只處理demo High且未指派Bug；新增needs-triage記錄行為與維護目的
Scope只選demo project規則允許在哪裡作用
Owner維護此規則的人負責管理與錯誤通知，不等於執行權限
ActorAutomation for Jira或明確選定的授權身分實際做變更並顯示於History的人
Notify on error依維護需求選擇不要用關通知掩蓋失敗
Enabled／Published完成檢查後啟用；編輯後Update草稿改了不代表生效

公司管理project的rule管理需要Administer Projects與Browse Projects，且global設定可限制project admin管理automation。Team-managed依Administrator access；跨project scope需Jira admin。這是管理規則的權限，不是rule執行時所有action的權限。

8．Demo lab：四個反例＋一次branch

以下由你在隔離demo操作；沒有代替你建立規則。先把Action暫設Log，文字為「candidate={{issue.key}} status={{issue.status.name}}」。驗證後才換成新增標籤。規則啟用後再建立測試卡。

測試預期
Bug、High、未指派通過，Log出現key；切換Add label後加needs-triage
Task、High、未指派不通過type條件
Bug、Medium、未指派不通過priority條件
Bug、High、已指派不通過assignee條件，不覆寫人工指派
在符合條件卡上先放existing-label，再執行等效Manual測試版新增needs-triage後existing-label仍在，證明沒有replace
另建Manual練習規則：Sub-tasks branch內Log「target={{issue.key}}, source={{triggerIssue.key}}」在一個含兩個sub-tasks的parent執行，看到不同target與相同source

若站台不允許Unassigned，可用另一個明確條件先練習並記錄差異，不必改全站設定。測完關閉自己的demo rules，避免未來demo資料意外觸發；不要關閉正式團隊規則。保存規則名稱、actor、測試keys與audit log時間。

9．原創中英情境題

1．需要新建Bug才執行，選？

  1. Issue created
  2. Scheduled每分鐘掃全站
  3. Issue deleted
查看答案與逐項解析

A。A精確對應事件；B多做不必要搜尋且語意不同；C是刪除事件。

English version

Run only when a bug is newly created. Choose.

  1. Issue created
  2. Scan the entire site every minute
  3. Issue deleted

A. A matches the event. B adds unnecessary searching and changes the semantics. C is a deletion event.

2．Related issues condition通過後，下一個Edit自動改所有sub-tasks嗎？

  1. 是
  2. 否，需要branch切換對象
  3. 只有改Priority才會
查看答案與逐項解析

B。A把檢查與迭代混淆；B正確；C欄位種類不會自動改上下文。

English version

After a Related issues condition passes, does Edit automatically edit every subtask?

  1. Yes
  2. No: use a branch to target them
  3. Only for Priority

B. A confuses testing with iteration. B changes context correctly. C has no such field-specific behavior.

3．在sub-task branch內，{{issue.key}}表示？

  1. 目前sub-task
  2. 原trigger issue永遠不變
  3. 全部sub-tasks的總數
查看答案與逐項解析

A。A是當前對象；B應用triggerIssue；C需要清單統計而非key。

English version

Inside a subtask branch, what is {{issue.key}}?

  1. The current subtask
  2. Always the original trigger issue
  3. The number of all subtasks

A. A is current context. B would require triggerIssue. C requires a collection count, not a key.

4．只要加一個Labels值且保留舊值，應？

  1. 使用Add/remove values中的新增
  2. 直接替換整個Labels欄位
  3. 先清空所有Labels
查看答案與逐項解析

A。A保留原集合；B與C會丟掉原標籤。

English version

Add one label and retain existing labels. Choose.

  1. Use the add operation under Add/remove values
  2. Replace the whole Labels field
  3. Clear all labels first

A. A preserves the original set. B and C remove existing labels.

5．Create issue之後直接Comment on issue，留言通常在哪？

  1. 剛建立的issue
  2. Trigger issue
  3. 隨機一張
查看答案與逐項解析

B。A要進created issues branch；B主路徑上下文未變；C不是隨機行為。

English version

Create issue is followed directly by Comment on issue. Where is the comment added?

  1. The newly created issue
  2. The trigger issue
  3. A random issue

B. A needs a created-issues branch. B retains main-path context. C is not random behavior.

6．最適合先驗證smart value輸出的動作？

  1. Log action
  2. 寄給全公司
  3. 刪除issue
查看答案與逐項解析

A。A可在audit log觀察；B造成不必要通知；C無法合理驗證輸出且破壞資料。

English version

Best action for first testing a smart value?

  1. Log action
  2. Email the entire company
  3. Delete issue

A. A exposes output in the audit log. B sends unnecessary messages. C destroys data without a useful test.

7．多筆related branches執行順序？

  1. 保證依issue key排序逐筆完成
  2. 平行且不保證完成順序
  3. 必定在主路徑下一步前全部結束
查看答案與逐項解析

B。A沒有此保證；B符合branch行為；C不可依賴，應重新設計資料相依。

English version

What execution order do multiple related-issue branches provide?

  1. Guaranteed issue-key order
  2. Parallel with no guaranteed completion order
  3. All finish before the next main-path step

B. A has no such guarantee. B is the documented behavior. C is unsafe to assume.

8．Owner與Actor的差別？

  1. Owner維護與收錯誤通知；Actor執行變更
  2. 兩者永遠同一人
  3. Owner自動取得所有project權限
查看答案與逐項解析

A。A區分責任與執行身分；B預設也可不同；C擁有規則不等於資料授權。

English version

How do Owner and Actor differ?

  1. Owner maintains the rule and receives error notices; Actor performs changes
  2. They are always the same user
  3. Owner automatically gets every project permission

A. A separates responsibility and execution identity. B is false. C confuses ownership with data authorization.
