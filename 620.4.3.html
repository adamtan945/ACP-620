LESSON 620.4.3 · AUTOMATION

排查 automation：先找執行證據，再縮小根因

分開檢查沒有觸發、條件不符、動作失敗與結果被覆寫。一次改一個原因，避免把範圍與權限愈開愈大。

考綱沿用 project／issue／issue type／rule；現行文件可能稱 space／work item／work type／flow。依功能辨認入口；先確認管理方式、權限與方案。下列互動均為本機模擬，實作步驟只供隔離的 demo site 跟做。

考綱目標：Troubleshoot Jira automation

1．不是每個「沒變」都代表同一种失敗

訂餐團隊規則應替High Bug加needs-triage，但某張卡沒有標籤。先問：audit log有沒有這次執行？進到哪個condition？Edit動作成功嗎？History裡是否被後來另一條規則覆寫？先把問題定位，才能做小而有效的修正。

本節完成標準：你能用一個audit log entry、觸發issue、actor與失敗step，說出可驗證的根因假說。不是看到沒結果就先給admin或放大成global rule。

2．Audit log：先看有沒有執行，再看每一個step

從Project settings → Automation開規則，進Audit log；也可查看project或global層活動。找出正確時間與issue，展開單筆執行，記錄status、rule名稱、audit log ID與每步細節。現行官方保留過去90天，重要診斷證據要在期限內保存，不能假設永久可查。

觀察可能意義下一個檢查
完全沒有entry沒觸發或被trigger篩選排除Enabled、已發布版本、實際事件、範圍、trigger限制
Condition不符合／沒有動作可能是預期排除，不一定錯誤實際欄位值與條件；對照正反例
Action顯示失敗已觸發但特定操作被拒絕或資料無效詳細錯誤、Actor、目的欄位與workflow
Success但看錯張卡上下文或branch選錯Log issue.key與triggerIssue.key
先改對後又變回另一規則或使用者後續修改對照issue History時間與其他audit entries
THROTTLED／limit類錯誤服務或用量限制限制類型、搜尋筆數、排程密度與branches

Audit log總時間包含處理與等待，不能只把每步時間加總當作使用者感受到的延遲；平行branches也使數字有不同意義。先用log定位行為，不把UI顯示時間當成精確效能實驗。

3．Actor的權限，不是Owner的權限

Actor是執行修改的身分，預設常見Automation for Jira；Owner主要維護規則與接收錯誤通知。你本人能Edit，不代表Actor也能Edit。JQL condition的Validate query使用你的權限，但rule執行使用Actor的權限，因此驗證按鈕有結果仍不能證明執行一定成功。

動作至少要檢查常見根因
讀取／搜尋issuesBrowse Projects以及issue security／accessActor看不到被限制的工作
Edit欄位Edit Issues；特定欄位另需對應權限一般可編輯不等於可改Reporter／Due Date
AssignActor能Assign Issues；被指派者是Assignable User把操作者與目標使用者的角色混淆
Create目的project Browse與Create Issues跨project的新卡類型或必填欄位不符
TransitionTransition Issues及workflow可用transition、conditions、validatorsActor不符合角色條件，或缺少必填欄位
CommentAdd Comments與適當可見範圍Actor不能留言或限制設定不符
更改規則ScopeJira admin在global配置Project admin不等於能把規則擴到所有project

詳見 project與global permissions。若Actor是Automation for Jira，檢查與該app身分相關的授權來源，不要把它當成無限權限的system root。修改共用permission scheme會影響其他project；用現有角色授予必要能力，並由admin核對。

Project admin通常只能把Actor設成自己或Automation for Jira；global admin能選其他使用者。若其他人是Actor，project admin編輯還有相應限制。把Actor換成高權限帳號可能讓測試通過，卻掩蓋錯誤的存取設計，不是預設解法。

4．Scope、query與related issue是三個不同條件

FOOD issue連到OPS issue，不會讓單project rule自動獲得OPS範圍。要跨project處理，需multi-project或global rule，且Actor在OPS也有必要權限；只改JQL成project IN (FOOD, OPS)不等於擴大rule scope。反過來，global scope也不會讓錯的query找對資料。

Scheduled的JQL、trigger filters與一般conditions各自限制集合。尤其「只含上次執行後有變更的issue」選項，對需要每天重新評估due是否逾期的規則未必適合：昨天沒逾期、今天變逾期的卡，欄位可能根本沒更新。先確定需求是追事件還是追時間。

互動診斷：手動編輯會觸發B規則，A規則編輯卻不會，先查？

查B的Allow rule trigger／Allow flow trigger。是否允許其他automation引發它，是獨立設定。不要直接開啟所有規則互相觸發；先畫A→B的事件關係，避免B又改回A監看的欄位形成循環。

5．欄位、smart values與workflow：已進action也可能失敗

症狀檢查修正方向
smart value輸出空白觸發情境有沒有該物件、欄位是否空、名稱／ID用Manual + Log印出最小路徑；合理fallback
剛Edit後讀到舊值issue資料快照尚未更新需要最新值的步驟前Re-fetch issue data
標籤被清空只剩新值Edit用set／replace模式改Add/remove values並驗證原值保留
新卡建立成功但留言在原卡主路徑未切換context使用created issues branch
Transition失敗目前status是否可到目的、conditions與validators使用存在的transition並補合法必填資料
欄位不能設定／無效值field context、screen、type、選項是否存在用目的project/type的實際欄位與值
分支後讀不到變數branch隔離與非同步執行別依賴跨branch共享狀態；改集合式查詢
target={{issue.key}}
source={{triggerIssue.key}}
status={{issue.status.name}}
labels={{issue.labels}}

這段Log只印診斷必要資訊。不要把完整描述、機密值或大量個資倒進audit log。若欄位名稱相同但context不同，能在來源project使用不代表目的也能用。Rule的JSON進階編輯也不會繞過資料型別與必填限制。

6．限制與重複執行：先縮小工作量

區分「方案每月用量」與「單次／服務限制」；看到THROTTLED先讀哪一類限制，不要猜一定是方案太低。現行Lookup issues只使用前100筆；Scheduled JQL另有搜尋限制，不能把二者視為同一種搜尋。具體門檻可能更新，以來源與站台Usage為準。

設計問題為何出問題改善
每分鐘掃全站所有Bug重複讀取大量不相關工作改必要頻率、限定project／狀態／條件
為每個type建立大型related branch只用來檢查增加關聯項目與queue能用condition／If/else就不用branch搜尋
每次更新都加同一段comment重複事件造成重複副作用加處理標記或判斷目標狀態，設計可重跑行為
A改Priority觸發B，B再改回Priority互相引發迴圈限制事件方向與條件；不要靠loop limit當正常流程
以Lookup前100筆當完整統計超過限制的工作沒納入縮小可證明完整的集合或分批設計並查證總數
把大量一次清理做成永久Scheduled rule長期消耗且有誤觸風險必要時採分批Bulk change，一次操作後結束

Audit log出現loop或throttle需要修正結構；先暫停自己正在測試的規則、保留證據，再減少trigger頻率與query範圍。不要反覆重跑同樣的大規則期待它偶然通過。關閉只影響後續觸發，已發生的變更不會自動還原。

7．Demo lab：一次製造一種差異，練習根因定位

延續上一節的隔離Manual規則，只作用於demo標籤或明確key。先用Log為主，任何修改也只改自己的測試卡。若無管理權，閱讀下列預期並記錄差異，不需要改正式permissions。

實驗動作預期與解讀
A：不符條件條件設Priority=High，對Medium卡手動執行有execution但在condition停下；不是trigger沒有發生
B：錯誤欄位路徑Log暫印{{issue.notARealField}}，再改{{issue.key}}前者空值，後者有key；證明smart value可單獨測
C：快照更新Log Priority → Edit Priority → Re-fetch → Log Priority最後讀到新值；把依賴最新值的步驟放re-fetch之後
D：上下文在parent的Sub-tasks branch印target與source各target不同而source相同；驗證實際操作對象
E：Actor權限只在已授權的獨立demo權限模型中比較具與不具Edit的actor；若無此環境略過Log可能仍成功，但Edit被拒絕；管理rule與執行Edit是兩種能力
F：重跑安全把新增標籤規則手動執行兩次標籤集合應一致；若加入comment則可能兩次留言，需另設重複判斷

驗證表記下：rule版本／名稱、Actor、觸發key、預期、audit log ID、實際結果與History。只在錯誤已定位後更動一個設定，再重測原失敗案例及一個原本應被排除的案例；最後關閉demo規則。

8．原創中英情境題

1．自己Validate JQL有結果，但執行沒有，可能？

  1. 驗證用本人權限，執行用Actor權限
  2. JQL永遠不能用在automation
  3. 只要換dashboard就好
查看答案與逐項解析

A。A是兩種不同執行身分；B與功能相反；C不處理automation搜尋的權限。

English version

JQL validates for you but returns nothing during execution. Why might this happen?

  1. Validation uses your permissions; execution uses the actor
  2. JQL cannot be used in automation
  3. Changing dashboards fixes it

A. A identifies different identities. B contradicts the feature. C does not address automation search permissions.

2．期待有執行，但audit log完全沒有，先查？

  1. Enabled、trigger與scope
  2. 先改所有欄位
  3. 刪rule重建
查看答案與逐項解析

A。A先定位有沒有觸發；B不必要；C丟失原配置且沒有診斷。

English version

An expected run has no audit entry. Check first.

  1. Enabled state, trigger and scope
  2. Change all issue fields
  3. Delete and rebuild the rule

A. A checks whether execution began. B is unnecessary. C loses configuration without diagnosis.

3．Condition不符所以沒做action，代表？

  1. 可能是正確排除
  2. 一定是系統故障
  3. 應移除所有conditions
查看答案與逐項解析

A。A需對照需求判斷；B無根據；C可能讓不該改的工作被修改。

English version

A condition fails and no action runs. What does this mean?

  1. It may correctly exclude the item
  2. It must be a system outage
  3. Remove all conditions

A. A depends on the intended criteria. B lacks evidence. C can modify unintended items.

4．FOOD單project rule要改linked OPS issue，僅加OPS的JQL夠嗎？

  1. 夠
  2. 還需scope涵蓋與Actor必要權限
  3. 只有連結type重要
查看答案與逐項解析

B。A把query當scope授權；B兩層都需要；C連結不會授權跨project。

English version

Can a FOOD-only rule edit a linked OPS issue just by adding OPS to JQL?

  1. Yes
  2. Scope and actor permissions must also cover it
  3. Only the link type matters

B. A treats a query as authorization. B requires both layers. C ignores project boundaries.

5．Edit後smart value仍舊值，適合？

  1. 在依賴新值前Re-fetch issue data
  2. 反覆加十個Delay
  3. 把Owner換人
查看答案與逐項解析

A。A更新資料快照；B沒有直接處理快照來源且依方案受限；C不改資料更新行為。

English version

After Edit, a smart value still shows old data. Choose.

  1. Re-fetch issue data before dependent steps
  2. Add ten delays
  3. Change the owner

A. A refreshes the snapshot. B does not directly refresh it and may be plan-limited. C does not change data freshness.

6．Assign失敗時要區分哪兩種能力？

  1. Actor的Assign與目標的Assignable
  2. Owner名字與project顏色
  3. 只要Creator有admin即可
查看答案與逐項解析

A。A分開操作者與被指派者；B無關；C原建立者權限不能代替執行Actor。

English version

Which two capabilities matter for assignment?

  1. Actor can Assign; target user is Assignable
  2. Owner name and project color
  3. Creator being an admin is enough

A. A distinguishes operator and target. B is irrelevant. C cannot replace the execution actor.

7．手動改欄位觸發B，A規則改卻不觸發，先查？

  1. B的Allow rule/flow trigger
  2. 所有users改成admin
  3. 把A排程成每秒
查看答案與逐項解析

A。A控制其他automation能否引發B；B過度授權；C增加負載且未處理觸發設定。

English version

Manual edits trigger B but edits by rule A do not. Check.

  1. B allows rule/flow triggers
  2. Make all users admins
  3. Run A every second

A. A controls automation-triggered runs. B grants excessive access. C adds load without fixing that setting.

8．Lookup issues回傳100筆，可以直接當作全站Bug總數嗎？

  1. 可以
  2. 不能，需確認query與100筆上限
  3. 只要log是Success就完整
查看答案與逐項解析

B。A忽略上限與scope；B需證明集合完整；C成功表示該動作執行，不證明全量。

English version

Lookup issues returns 100 items. Is that the total count of all bugs?

  1. Yes
  2. Not without checking query scope and the limit
  3. Success guarantees completeness

B. A ignores limits and scope. B requires evidence of completeness. C confuses successful execution with exhaustive results.
