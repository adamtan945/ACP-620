考綱目標：Analyze information from agile reports and issue analysis reports

1．打開報表前，先核對四件事

訂餐團隊說：「我們每天都有完成工作，為什麼 Burndown 沒下降？」可能是中途加工作、改估算、完成狀態沒有映射到最右欄，也可能只是看錯 board。先檢查定義，再評價團隊。

本節經典 Agile reports 主要以 company-managed boards 為例。現行 Reports 可能先開啟 space insights，再按 More reports 進經典目錄；space insights 用整個 project 的資料，不隨所選 board filter 限縮。Team-managed 的可用報表不同，依 Reports 目錄與是否啟用 sprints 確認，不要把 company-managed 的完整清單當成每個 project 都有。

先複習 columns 與 workflow、estimation 與 time tracking。對這裡討論的 board-based 完成統計，最右欄映射特別重要；Resolution 是另一欄位，會影響通用 issue analysis。

2．先選報表：要看 sprint、長期範圍，還是流動速度？

問題報表典型適用範圍
本 sprint 還剩多少BurndownScrum sprint
新增範圍是否抵銷完成量BurnupScrum sprint；完成線與總範圍線
這期哪些做完、未完成、移出Sprint ReportScrum sprint 回顧與逐筆核對
過去每期能完成多少估算量Velocity ChartScrum 已完成 sprints
某 Epic 還有多少未完成與未估算Epic ReportScrum；跨多個 sprint 的單一 Epic
Epic 可能還要幾期Epic BurndownScrum；以歷史進度與剩餘估算推測
Version 可能何時完成Version ReportScrum；日期預測與總範圍
Version 可能還要幾期Release BurndownScrum；以 sprint 呈現 release 進度
流程耗時及變異是否改善Control ChartScrum／Kanban；依所選欄位、日期、篩選器
工作堆在哪個流程階段Cumulative Flow Diagram（CFD）Scrum／Kanban；隨時間觀察各欄累積

Kanban 沒有因為叫 Agile board 就自動得到 Sprint Report 或 Velocity。不同報表的計算期間與資料範圍不一樣，不能把兩張圖的數字直接視為應該相等。

3．用一個 20 點案例區分 Burndown 與 Burnup

假設 sprint 開始有20點；完成5點後新增8點，再移出3點未完成工作。全部是可計入的標準 issues，沒有改估算或 reopen。這是原創數值示意，不是 Jira 截圖。

事件總範圍累計完成剩餘
Sprint 開始20020
完成5點20515
新增8點28523
移出3點未完成工作25520

最後剩餘回到20，不代表大家沒工作：已完成5點，但淨新增範圍也是5點。Burnup 把 scope 與 completed 分開，兩線距離就是剩餘量；Burndown 聚焦剩餘量，看到上升要查新增、估算調整等事件。時間追蹤配置下剩餘工時變更也會影響曲線，不能把每次下降都解讀為卡片 Done。

Guideline 是完成整期工作的大致參考，不是績效標準。Working days 會影響 guideline 的非工作日呈現；每日實際曲線不必平滑。依 620.2.5 核對 board 的 estimation／tracking 配置後再判讀。

Sub-task 要另判斷：Story Points 不納入 Burndown 的 parent points 統計。若 board 啟用 Remaining Estimate and Time Spent，sub-task 工時會向 parent 彙總；active sprint 中新增 sub-task 的 scope change 也會反映。未啟用時不以同樣方式顯示其 scope change。別把「Story Points 不計 sub-task」誤記成「所有報表一律不看 sub-task 工時」。

4．Sprint Report 與 Velocity：承諾量不是最後總量

Sprint Report 讓你回到工作清單，查完成、未完成與移出情形；開始後加入的工作以星號標示，估算變更可能顯示「原值 → 新值」。這比只看曲線更能解釋 scope change。Sub-task estimates 不列入 Sprint Report 的 parent estimates 統計。

Velocity 的 Commitment 是 sprint 開始那一刻的總估算，之後新增或改估算不回寫該欄；Completed 是結束時完成的估算，會受期間 scope changes 影響。因此 Completed 大於 Commitment 可以是臨時加入工作完成，不是數學錯誤。Velocity 不納入 sub-task estimates。

期別開始 Commitment結束 Completed解讀
Sprint A2018完成量略低於起始承諾，還需看移出與加入
Sprint B2026可能完成額外範圍；不能只說承諾估得太小
Sprint C2422三期平均完成量=(18+26+22)/3=22

此例22點是教材的三期平均，用於大致規劃下一期；不是官方保證能完成的數量。團隊估算尺度、人員或工作類型改變時，可比性下降。Story Points 不適合拿來排跨團隊個人績效。

5．Epic 與 Version：範圍、未估算與預測

Epic 回答一塊大型需求的進度；Version 回答一個交付版本的進度，同一版可以包含不同 Epics 的工作。管理版本與 Timeline 的實作見 620.3.3。

報表看哪個訊息判斷限制
Epic Report完成、未完成、未估算的子工作看到低剩餘點數先查是不是很多工作根本沒估
Epic Burndown各 sprint 的完成、剩餘、增加範圍，與預測 sprints預測使用近三期的該報表計算；不是直接照抄 Velocity Chart
Version Report總量、完成量與預測日期區間排除 sub-task types；可顯示 released versions，不顯示 archived versions
Release Burndown版本工作跨 sprint 的完成與 scope changes未映射 status 的工作不列入該報表；planned version dates 不決定所有 bars

Epic／Release Burndown 預測只根據可估算且已估算的工作。官方以未估算比例超過30%標紅提醒，但低於30%也不等於可靠。未估算不是0工作量。預測速度使用近三期，通常不含當期；當期完成量已超過預測時有例外。這種計算與 Velocity Chart 的平均完成量不同。

Version Report 要有至少10%估算工作完成才能計算預測，樂觀／悲觀區間使用速度調整。這是產品模型，不是承諾交期。新增需求、重估與 reopen 都可能改變結果；版本原本排定的 Release date 不會強迫團隊在那天完成。

考綱前言另提 Advanced Roadmaps 與 Jira Align。這些屬跨團隊規劃脈絡，不是另一種 sprint report；本節不把 Plans、單 project Timeline 或 Jira Align 當作相同產品。需要跨團隊依賴與策略協調時，應先釐清規劃範圍，再核對目前方案與工具。

6．Control Chart 與 CFD：速度和塞車是兩種問題

Control Chart 以各 issue 在所選欄位／狀態的經過時間呈現 cycle time；若把從建立到完成前的階段都納入，才接近 lead time。X軸是離開所選狀態的時間，Y軸是耗時。點可能代表單一工作或群集；rolling average 與標準差帶協助看變化與離散程度。

例如選 In Progress + Review：工作待辦3天、開發2天、Review4天，所選流程耗時為6天，不能把它說成含待辦的9天。若 reopen 後又在所選狀態待1天，相關工作時間也要算。選錯欄位、不同工作類型混在一起，都可能讓比較失真。

官方 rolling average 是以工作項目為窗口，不是固定七天平均。報表也可能包含尚未整體完成、但已離開所選欄位的工作；要只看已完成，另外使用合適的 quick filter。異常點先查原因，不能只為了讓均值好看就排除真實困難案件。

CFD 概念如何讀不要誤解
橫軸時間，縱軸 issue 數各色帶對應 board 欄位不是 Story Points 估算總量
某色帶垂直變厚該階段累積工作增加，值得查瓶頸不能光看圖就斷定某個人偷懶
最上方界線成長整體納入範圍可能增加不是所有新增都等於已完成
顏色帶的厚度相鄰累積界線之差呈現該段工作不要把累積邊界數字當成每欄當下卡數

這是以每日快照繪製的原創 CFD 教材圖，週三 Review 上界是12，但 Review 只有12−5＝7件；底下5件是Done。下一步查 review 等待原因、批次處理方式、WIP 與人力，不要直接調高 WIP limit 把警示藏起來。

7．通用 issue analysis：Resolution 與時間口徑

報表適合回答常見誤讀
Average Age未解決工作已存在多久不是已完成案件的平均處理時間
Created vs Resolved某段期間進件與解決數量兩條線不是同一批建立日 cohort
Recently Created每個建立時段那批新工作，有多少已解決不能直接當成當天解決了幾件
Resolution Time已解決工作從建立到解決花多久不是 Control Chart 所選欄位的 cycle time
Pie Chart某集合依一個欄位分布件數占比不是工作量占比
Single Level Group By按欄位分組列出 filter 結果是清單分組，不是 sprint 預測
Time Since Issues選定日期欄位在各時段出現的件數欄位選 Created 與 Resolved 會回答不同問題
Time Tracking版本估時、已耗時、剩餘與估算差異需要啟用 time tracking 且資料有版本
User／Version Workload指定人員或版本的未解決工作與剩餘量不是比較 Story Points 績效
Workload Pie Chart以時間資料觀察負責人相對負荷先確認 gadget／report 的實際計量欄位

Resolution 表示為何結束，例如 Fixed、Duplicate、Won’t Do。流程把工作移到最右欄卻未設定 Resolution，可能造成 Agile report 視為 Done，但未解決統計還納入。反過來，reopen 沒清空 Resolution 也會讓統計失真。公司管理流程需與 Jira admin 合作修正，不要為了報表直接在一般編輯畫面亂改欄位。

project = FOOD AND statusCategory = Done AND resolution IS EMPTY

project = FOOD AND statusCategory != Done AND resolution IS NOT EMPTY

以上是檢查口徑不一致的候選清單，不代表每筆一定錯。狀態類別與 board 最右欄也不必然相同，要逐筆查 workflow 和 mapping。Time Tracking 可用 Original Estimate=8h、Time Spent=5h、Remaining=6h 理解：目前預計總耗時11h，比原估多3h；不能說「剩3h」因為原估減已耗不是目前 Remaining。

8．互動診斷：先猜原因，再展開

每天有 Done，Burndown 卻持平

先對照事件清單：新加入的估算是否抵銷完成量？是不是改估算？Done 狀態是否在最右欄？若按剩餘工時追蹤，Remaining 是否確實更新？最後才評估團隊是否過度承諾。

Epic 只剩2點，可是還有8張未估算

2點只代表已估算且剩餘的部分。先補足拆解與估算，或清楚說明未知範圍；不可以告訴主管「一定這期完成」。

CFD 的 Review 帶擴大，但 Control Chart 平均變短

兩者不矛盾：前者看累積，後者的樣本可能只是已離開所選欄位的較快工作；仍卡住的長尾未完整反映。對照期間、欄位、filters 和樣本，不要只挑較漂亮的一張。

9．Demo lab：一個短 sprint，驗證 scope 與完成判定

使用隔離 company-managed Scrum demo board，不操作正式 sprint。若無建立權限，請在已核准的練習 project 做；若只有 team-managed，先完成可用的 Burnup，並記錄報表差異。需要的欄位與權限見 620.2.5、620.3.1。

步驟預期觀察
建立兩張標準 Story，分別5點與3點；建立測試 sprint，開始前加進去開始總估算8點；先確認 estimation=Story Points
把5點 Story 移到最右欄的 DoneBurnup 完成量升至5；若 points burndown 剩餘量可見，剩3
開始後加入2點 Story總 scope 升至10；剩餘升至5；Sprint Report 顯示後加標記
保持3點 Story 未完成；把2點 Story 也完成，再結束測試 sprintVelocity Commitment=8、Completed=7；未完成3點依結束畫面移回 backlog或下一期
對照 Sprint Report 的逐筆清單與估算應可解釋8與7為何不同：5+2完成，3未完成
觀察 Control Chart，記下所選欄位、期間與樣本短時間測試只驗證納入與欄位，不足以證明長期cycle time 趨勢

本教材未連線替你開始或結束 sprint；上述預期依示例沒有其他資料、重估、reopen 與過濾差異。若數字不同，先查 board filter 是否漏卡、status 是否 unmapped、estimation 是否一致。保留一份實驗記錄，別透過修改正式 board mapping 追求圖形一致。

10．原創情境題與逐項解析

1．開始20點，完成5點，再新增5點；剩餘仍20點，最合理？

  1. 團隊沒有完成任何工作
  2. 新增抵銷完成量
  3. Jira 一定算錯
查看答案與逐項解析

B。A 忽略已完成5點；B 符合20−5+5=20；C 沒有必要假設錯誤。

English version

Start with 20 points, complete 5 and add 5. Remaining work is still 20. Why?

  1. No work was completed
  2. Added scope offsets completed work
  3. Jira must be wrong

B. A ignores the five completed points. B follows 20 minus 5 plus 5. C is unnecessary without evidence.

  2. Assigned To Me
  3. Activity Stream

A。A 將 scope、completed 分兩線；B 是個人清單；C 是事件動態，沒有這個估算對照。

English version

Compare total scope and completed work separately. Choose.

  1. Burnup
  2. Assigned To Me
  3. Activity Stream

A. A displays scope and completion separately. B is a personal list. C shows activity, not this estimate comparison.

3．Sprint 開始8點，後加2點且全部完成，Velocity Commitment？

  2. 8
  3. 0
查看答案與逐項解析

A sprint starts with 8 points. Two more are added, and all work completes. Velocity Commitment?

  1. 10
  2. 8
  3. 0

4．Done status 未映射最右欄，Agile report 沒當成完成。先做什麼？

  3. 把 issue 改名 Completed

English version

Done status is not mapped to the rightmost column and work is not counted complete. First check?

  1. Board column mapping
  2. Only Resolution
  3. Rename the summary to Completed

A. A determines completion for these board reports. B affects general reporting but cannot replace mapping. C does not control progress.

5．Kanban 團隊要找流程塞在哪，適合？

  1. CFD
  2. Velocity Chart
  3. Version 的名稱排序

6．Control Chart 選 In Progress 與 Review，是否自動包含所有 To Do 等待？

  1. 是
  2. 否，時間依所選狀態
  3. 只要 issue 有 assignee 就包含
查看答案與逐項解析

B。A 把 cycle 與 lead 邊界混淆；B 正確；C assignee 不決定所選欄位範圍。

English version

Control Chart selects In Progress and Review. Does it automatically include all To Do waiting time?

  1. Yes
  2. No: elapsed time depends on selected statuses
  3. Only if an assignee exists

B. A confuses cycle and lead-time boundaries. B is correct. C does not determine selected columns.

7．Epic 預測還要一期，但多數 issues 未估算，應？

  1. 直接承諾一期
  2. 說明預測缺少未知工作量並補估
  3. 把未估算工作全部刪除
查看答案與逐項解析

B。A 過度解讀；B 改善預測輸入與表達；C 破壞範圍且隱藏問題。

English version

An epic forecast says one sprint remains, but most work is unestimated. What should you do?

  1. Promise one sprint
  2. Explain missing scope and improve estimates
  3. Delete all unestimated items

B. A overstates the forecast. B improves inputs and communicates uncertainty. C hides scope and destroys useful information.

9．同一 project 的 space insights 與 classic board report 件數不同，可能？

  1. 前者全 project，後者受 board filter 範圍影響
  2. 必定有人刪資料
  3. 兩者永遠應相同
查看答案與逐項解析

A。A 是現行入口的重要範圍差異；B 不能由件數差直接推論；C 忽略了各自資料定義。

English version

Space insights and a classic board report show different counts for the same project. Why might this happen?

  1. Insights cover the project while the classic report can be scoped by the board filter
  2. Someone must have deleted data
  3. Both always have identical scope

A. A identifies a current scope difference. B cannot be inferred from a count mismatch. C ignores each report definition.

10．原估8h，已記錄5h，Remaining6h，目前預計總耗時？

  1. 3h
  2. 11h
  3. 8h
查看答案與逐項解析

B。A 只是8−5，並非目前剩餘；B 是5+6；C 是原始估算，尚未反映新資訊。

English version

Original estimate is 8h, time spent is 5h and remaining estimate is 6h. Current total forecast?

  1. 3h
  2. 11h
  3. 8h

B. A subtracts spent time from the old estimate and is not current remaining work. B adds 5 and 6. C is the original estimate before new information.
